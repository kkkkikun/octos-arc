## 2. 比赛与计分

- 赛事：GOSIM Factory26 黑客松，平台 arc-bench.com。截止 2026-10-03 23:59（已两次
  延期）。参赛须知（9/21 版）：前 20 名晋级决赛。
- 任务：两个 web 应用构建任务，独立计分：
  - **sheet**：类 Excel 在线表格，25 个需求节点 / 100 个评测场景；
  - **github**：类 GitHub 协作平台，45 个需求节点 / 100 个评测场景。
- 计分：**S = p·(B/b)^0.2**。p=该跑通过率，b=该跑 Meter 实测花费（人民币），
  B=任务固定预算（具体值未知；早年练习榜反推约 ¥13/任务，未经正式赛验证，仅供
  量级参考）。
- **每任务取历史最高分跑**：已入账分数保底，新跑下行风险为零（只会白花钱、不会
  掉分）——后期票理应越打越激进。
- 直觉刻度（0.2 次幂）：b 省一半 → S×1.15；b 翻倍 → S×0.87；p 翻倍 → S×2。
  p 近线性主导，b 是弱奖励。
- 边际规则（我方对公式求导）：继续花 Δb 当且仅当 Δp > 0.2·p·Δb/b；在我方操作点
  （sheet p≈25 场景、b≈$6.5）化归为 **≈1 场景/美元** 的盈亏平衡。
- 排行榜对照（问题所在）：我方 b = github ¥64.8 / sheet ¥65.5；全场他人
  github ¥30-50 / sheet ¥20-50；且我方 p 显著更低——p 与 b 双输。历史跑无成本闸，
  b 偏高主因是"无望节点的修复马拉松"（已机制化切除，见 §5）。

## 3. 平台机制与硬约束

- 提交物 = 一个 zip：harness 代码 + 通用模板 + 我方自己的"公共测试"（代理测试）。
  每票 = 一次提交；跨任务可并行（两任务曾同时发车）；同任务在跑票未结束前能否
  再提新票未验证（按串行规划保守处理）；单任务墙上限 48h。
- 每跑全新容器：平台跑我们的 main.py → 自举 → 构建应用 → 平台用**隐藏官方测试**
  对最终交付物评分（只看交付物，不看过程）。平台与本地无状态互通；合规禁止任务
  特定预置（只许通用脚手架），所以我方"自举接力"只在本地迭代有效，平台每跑都是
  冷启动。
- 中途被杀也能交付：每 60s 渐进交付最后一次通过检查的状态。
- 官方真实测试从未流出。社区发现 github 官方测试与需求文档不对应（赛方因此延期）；
  **需求文档是唯一真相**。我方包内 public-tests 是 Agent 依文档写的代理测试
  （github 44 spec + sheet 24 spec，已全量审计、修 7 处硬伤，结构性红名单见 §7）。
- 模型：平台跑现用 deepseek-v4-flash（平台网关，harness 内可做模型路由）。
  实测 ~69 tok/s 有效出活速度，难节点单次实现轮 ~20 分钟。
- 评测容器 1 核 / 2GB，Chromium + Playwright，单场景测试钟 40s（官方 helper
  串行探测角色，更短的钟曾连续误杀合法 spec）。
- 资源：剩余预算 ¥434；汇率口径 $6.5≈¥47。

## 4. 系统架构速写

```
提交 zip
 └─ main.py（python 适配器，只做粘合，无编排逻辑）
     1. 读平台环境变量与路径；
     2. requirements.yaml → 原子需求节点 → 依赖序链式 DAG
        （每需求 1 个实现节点 + 1 个验收节点；验收失败 → 回边 → 修复轮）；
     3. 启动 Rust 内核并把该 pipeline 点名交给它；
     4. 收集内核事件成报表。
 └─ octos-pipeline（Rust 内核）DAG 调度器真正执行 实现→验收→修复 循环
    （回边重试只有 DAG 调度器会做；一切策略旋钮集中在 arc-policy.toml）
 └─ verify_node.py（验收器，单节点命令）：构建 app → 起服 → 跑该节点的代理
    Playwright spec → exit 0/非0 即判决，stdout 全文回传给修复轮当反馈
```

## 5. 机制清单（名字 → 干什么 → 为什么）

- **链式 DAG**（main.py）：需求按依赖序排链 → 节点序即难度序，尾部时间 reserve
  保护未跑的下游。
- **修复回边**（内核）：验收失败的输出交回实现节点 → 修什么、怎么修有具体反馈，
  而非盲目重写。
- **逐场景隔离启动 + 种子快照恢复**（verify_node.py）：官方 spec 是有状态对，共享
  启动会互杀；跨测试状态污染靠每测试还原种子兜住 → 套件因此非幂等，是设计而非缺陷。
- **回归金丝雀·挣得绊线**：某需求族只有本跑已过检才派金丝雀回归 → 防冷跑全冻结
  （历史 bug：金丝雀全派 → 有状态对互杀 → 检查全灭 → 交付冻结在极早态 = 6/100 之一）。
- **js 语法刀**：每路由脚本解析烟雾测试 → 历史上相对路径 404 拿回 HTML 让 JS 全灭，
  静态存在性 lint 看不见这类死。
- **asset-hole 探针**：引用的根绝对 .js/.css 404 即败 → 历史上路由白名单漏一个
  静态文件导致全站 JS 死、评分全灭。
- **停摆刀**：连续 2 轮场景得分签名不动 → 节点弃修（签名动了则清零重计）→ 砍
  "无望节点修复马拉松"（¥65/12h 尸检的头号浪费源）。
- **燃料表**：内核 meter 实时花费 ≥$6.5 → 停世界、交付已验证态（防呆双闸：还需
  累计 10M+ token 且运行 15min+ 才触发）→ 直接钳 b；墙 24h 仅兜底。
- **渐进交付**：每 60s 落盘最后过检状态 → 任何时刻被杀都有分。
- **prompt 权威线**：文档 prose > 代理样例 → 样例可错（github 官方测试与文档
  不对应有先例）。
- **40s 测试钟**：官方 spec helper 串行探测角色需 ~40s → 10s 钟曾连续三代误杀
  同一 spec（在跑检查假阴性）。
- **本地同构验证**：同款模型+付费 key 在本地容器跑切片 → 免费道跑不了 github
  auth 族（付费 42 分钟全绿）；一切机制改动上平台前先在本地容器过一遍。

## 7. 已知结构事实与风险

1. github 验收地板 ≈900s×45 节点 ≈ 11.3h；sheet ≈ 6.3h。两者都小于 24h 墙。
2. 每任务取历史最高分：sheet 25、github 4 已保底。github 每涨 1 分都是净增
  （边际最肥）；sheet 需 >25 才有贡献，而冷启天花板恰在 25-26 —— sheet 新票的
   期望值完全取决于 24h 墙+双闸能否把冷启顶穿 26。
3. **sheet 模块种子互斥**（结构性红，不修）：REQ-3/4 族 ~25 场景在我方静态检查下
   恒红（单一静态种子无法同时满足 REQ-1/5 与 REQ-3/4 两个世界），但隐藏测试按
   场景重播种 → 评分无损，纯在跑摩擦（修复轮烧损，现由停摆刀封顶）。
4. 代理测试已知残余风险集中在"种子互斥/复用"类（7 处硬伤已修）；套件非幂等，
   裸跑 playwright 必连环红（快照恢复是承重墙）。
5. github REQ-6-3 评审人约束：评审人 ≠ PR 作者、作者须为独立账号 —— 对 app 种子
   的硬要求，实现侧照办即可。
6. 成本结构：钱 ≈ 实现节点重执行次数 × 单价（验收节点是 shell 检查，零 LLM
   token）；浪费大头 = 无望节点修复马拉松，停摆刀+燃料表双闸已机制化切除。
7. 冷启动瓶颈定位：6h 墙内 deepseek 建不完 25 节点（sheet）；墙是冷启抬升的
   唯一杠杆（48h 规则内有余量）。
