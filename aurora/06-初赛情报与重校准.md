## 二、计分公式（策略核心）

S = p·(1.2p/b)^0.1（b ≤ 1.2p）／ p·(1.2p/b)^0.2（b > 1.2p）；p=两任务合计通过率
百分数，b=Meter 实测总开销（**CNY**，已用 meter_snapshot.py 验证）。

| 场景 | p | b(¥) | S |
|---|---|---|---|
| 满分压线 | 100 | 120 | 100.0 |
| 满分半价 | 100 | 60 | **107.2** |
| 满分双倍 | 100 | 240 | 87.1 |
| 90 压线 | 90 | 108 | 90.0 |
| 90 双倍 | 90 | 216 | 78.3 |
| 95 超支 26% | 95 | 144 | 90.7 |

结论：① p 近线性主导，弱任务拖 p 代价 >> 省钱收益；② 奖励弱（省半 +7%）惩罚强
（双倍 −13%）；③ 预算线处**边际汇率恒为 ¥7.2 / 通过率点**（超支区 db/b=6·dp/p，
节余区 11·dp/p）——修复循环每点收益成本超过 ~¥7 即负优化，直接给 C1 的 repair
循环设了止损线。

成本口径（已查实）：我方 metrics 的 $ 数来自内核 `pricing.rs` 供应商公开价目
（deepseek 系 0.27/1.10 每百万，**USD** 估值；aurora/03 里个别行标 CNY 是笔误）；
正式 b 是 Meter **CNY** 实测、平台自有费率。锚点：本 key 7 天窗口 954.5M tokens /
¥358.98 ≈ 混合 ¥0.38/M。**精确换算：下次练习跑前后各一次
`python3 arc/meter_snapshot.py snapshot` 取差值**（若平台费率接近内核 USD 数值，
则 stackoverflow 级 T2 单题 ≈ ¥10 量级，双任务远低于 1.2p 预算线，p 才是主战场）。

## 三、官方 Runner 契约（本地模拟环境 = 生产 run_submission.py 的容器复现）

- 入口：`python3 main.py <requirements_dir> --output-dir <output_dir>`，退出码 0。
  我方 `arc/main.py` 兼容（`--web-port` 默认恰为 3000、`--type` 默认 web）✓
- **部署只有一条正式路径**：输出根须含 `frontend/`+`backend/`（各带 package.json）；
  平台执行 frontend `npm install --include=optional && npm run build`、backend
  `npm install --include=optional && HOST=0.0.0.0 PORT=3000 npm run start`。
  ⚠️ `deploy.sh` 是本地模拟专有 monkey-patch，**正式平台无此分支**——只产出
  deploy.sh 本地满分正式零分（README 官方自曝）。我方走 frontend/backend，无恙。
- 评测：Chromium、**workers=1**、**单测/expect 均 10s 超时**、baseURL 127.0.0.1:3000、
  应用就绪等待 120s（HTTP <500 即算就绪）。
- 资源：**1 核 / 2GB**（agent 运行+部署+评测同容器）——坑6 长跑内存对策的硬约束坐实。
- 环境：Node 20.19.3、Playwright 1.57、Ubuntu Noble、Python+常用包预装。
- Meter：`meter.arc-bench.com`，login(access_key)→usage(start,end)→logout，
  b = 前后快照差值（local_submit.py 已实现并落地同一计分公式）。
