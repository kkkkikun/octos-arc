# 04 · 优化循环与实验台账

2026-09-20 ｜ 方法论来自官方教程 PPT 第三/四部分，我方执行约定在此基础上具体化。

## 三原则（改之前先定方法，每步以运行数据为依据）

1. **定位问题**：读运行日志和度量数据，不做推测
2. **只修改一处**：一次只改一处（一段提示词 / 一个环境变量 / 内核一个函数），
   否则无法归因；改动必须注明针对哪个问题（现象 → 原因 → 修改）
3. **重新度量**：同一题目、同一模型重跑，对比改前改后；**本机全部通过后再提交平台**

优化按两个指标展开：**通过率、费用**。每个指标的改动都要说明现象、原因、修改、度量。

## 测试分级（2026-09-20 定，规模=ATOMIC 节点/spec 数）

| 级 | 用途 | 题目（规模） | 何时跑 |
|---|---|---|---|
| **T0 快速验证** | 改动后是否**退化**的快速检查 | smoke--counter、smoke--dice（各 1 节点/1 spec，~10min/$0.01） | 每次改动后 |
| **T1 初步标准** | 优化的主要度量基准 | arc-bench-web--keep（32/33）、arc-bench-web--bookstack（34/35） | 每次改动后（keep 为主，bookstack 辅） |
| **T2 中等标准** | 中等规模泛化验证 | arc-bench-web--stackoverflow（66/67）、arc-bench-web--prestashop（86/87） | 关键节点/存疑时 |
| **T3 最终实验** | 大规模改动门禁 | arc-bench-web--12306（117/118）➕ arc-bench-web--ctrip（125/126） | 仅大规模改动提交前 |

（`ticket-booking--ticket-booking` 是平台入门题 2 节点，不在此体系内。）

### 分级管理规则

1. **小规模修改**（提示词微调、参数调整）：T0 不退化 + T1 有提升 → 即可提交；
   commit 信息注明「验证至 T1-keep：xx→xx」这类有效范围
2. **大规模修改**（编排逻辑重构、内核改动）：必须走完 T3（12306➕ctrip）才能提交，
   同样注明有效范围（例：「验证至 T3：keep 18/33、12306 xx/118、ctrip xx/126」）
3. **如非必要尽量跑小测试**——大测试太耗时（T3 单题 117-125 节点，本机数小时级）
4. 提交平台前一律先本机全过（PPT 第四部分第③步）

## 台账纪律

- **未完成的运行记「未完成」，不记 0 分，也不记「成功」**
- 台账加一列「验证至」，与 commit 信息里的有效范围一致（T0/T1-keep/T2/T3）
- 改动同步记 `arc/CHANGELOG.md`（官方惯例，改前改后数据）
- 对比只在本机 vs 本机、云端 vs 云端之间做（两端环境不同不直接比）
- 题目/模型/内核版本任何一项变了，对比作废，重新立基线

## 实验日志留存（找优化点的原料，一律保留不删）

每次运行固定留三处，命名 = 台账「运行编号」：

| 位置 | 内容 | 用途 |
|---|---|---|
| `scratchpad/<run>.log` | 全程 stdout（节点/验收/修复/回归/收尾） | 流程级行为分析（修复轮数、回归点、跳过原因） |
| `scratchpad/<run>-run.sh` | 启动脚本（含预算/环境变量） | 复现与对照 |
| `arc/arc-output/<run>/.arc/` | 事件流原始件：`llm-usage.jsonl`（每请求 token/耗时/状态）、`octos-events.jsonl`（内核级事件）、`runner-events.jsonl` + `traceability/`（节点状态） | `metrics.py` 数据源；挖单请求耗时尖刺/重试/大上下文轮次 |

挖优化点的惯用查询：失败/修复最多的节点（`<run>.log` grep `repair`/`TEST FAIL`）、
上下文最大的请求（`llm-usage.jsonl` 按消息字符排序）、耗时尖刺（按 duration 排序）。
`scratchpad/`、`arc-output/` 均被 gitignore，只留本机；云端运行日志在平台 run 页面
归档（submission id 见 aurora/03）。
