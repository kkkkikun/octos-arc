## 四、本地 vs 平台：为什么差这么多

这是整个比赛最重要的一个对账，详见
[`arc/scratchpad/docworld-reconciliation.md`](../../arc/scratchpad/docworld-reconciliation.md)。

同一份 sheet 产物（平台 41/100），在四种评分配置下：

| 配置 | 语义 | 得分 |
| --- | --- | ---: |
| S2 套件 × 逐场景 GIVEN 世界注入 | 文档唯一自洽语义（各族 GIVEN 互斥钉死同名工作簿） | **102 / 103（99）** |
| S2 套件 × 静态自有 store，逐测恢复 + 重启 | 平台若不重播种 | 84 / 103（82） |
| 第一代读法套件 × 静态自有 store | 官方读法 × 无污染 | 77 / 100 |
| 第一代读法套件 × 静态自有 store × 单 boot 4 workers | 平台若共享会话评分 | 33 / 35 / 100 |
| **官方隐藏测试（平台实测）** | — | **41 / 100** |

结论：

1. **应用质量不是主因。** 逐场景注入世界后 102/103——功能完全跨世界成立。
2. **官方 41 的主体是评分语义**：世界失配约 −19 例，共享会话污染再 −40 余例。
3. 只有"共享 boot 分支"能复现 41 的量级（33-35 ± 噪声 vs 41）。
4. 应用侧唯一确凿缺口：粘贴拒绝文案 `from 0 to 100` vs 文档钉死的 `between 0 and 100`
   （4 处文档原句）。

github 同理：官方前 30 例 = **4 PASS / 26 FAIL**，本地代理 51/100。

**这个对账的意义**：它证明了我们的机制是有效的，同时说明"本地全绿"在平台
共享会话语义下**不可直接迁移**。头部队伍用"自写测试 + 源码级契约检查"绕开了
这个陷阱（他们的测试在环内、在同样的共享语义下跑）。
