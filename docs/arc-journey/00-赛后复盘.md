## 二、三支队伍各做对了什么

### 2.1 VOLO-AI —— 减法做得最狠的一支

仓库：[thunderstone-group/volo-factory-finals](https://github.com/thunderstone-group/volo-factory-finals)

他们有一句自我描述，值得逐字读：

> "VOLO Factory 是一个多轮工具循环……可一换成 Keep 这样的大题，一局要一百多次
> 调用、八到十二块钱，最好也只有 25/32。"

> "同一道 Keep：多轮循环跑了 186 次调用，22/32、12.03 元；**一次调用加一张
> 『方言卡』，27/32 和 29/32，每次不到 1 元**。当天刚定下的 TypeScript 内核重写
> 和 Prime Agent 适配一起停掉，入口只剩一次起草。"

**他们和我们的起点几乎一模一样**：多轮工具循环、逐节点自检修复、大题成本爆炸。
区别是他们在 **09-15**（比赛开始前 9 天）就做了这个减法，我们在整个比赛期间
都没有做。

他们的四步最终架构：

| 步骤 | 进入架构 | 做什么 |
| --- | --- | --- |
| **一次起草** | 09-15 | 需求、方言卡、旧源码放进**同一个请求**，温度 0 |
| **自写测试** | 09-25 | 同一模型**看不到应用**，只读需求写 Playwright 测试 |
| **有界修复** | 09-23 | 定点编辑 SEARCH/REPLACE，**每丢 1 条至少多过 3 条**才接受，24 次调用 / ¥10 封顶 |
| **守卫交付** | 10-06 | **不调模型**：重放旧行为、核对需求写明的位置，永不交付空 |

四个我特别想记下来的机制：

**① 知识阶梯（ADR 0001）。** 他们把每个失败族按"最低能承载它的载体"分层：

```
门禁（代码检查 + 有界修复） > 随包发布的脚手架原语 > 从需求算出来的表 > 提示词里的散文规则
        ↑ 优先                                                          ↓ 最后手段
```

原文：*"A prose rule is the last resort, not the first."*

对照我们：`prompts/pipeline-implement.md` 有 **13KB**，大量规则写在散文里靠模型
"记住"。我们做了 `aria_lint` 这个门禁（方向对），但只覆盖"可访问名"一类。

**② 3:1 修复接受规则。** 原来是"只增不减"（修复不能丢测试），读数推翻了它：

> "修好路由的修复让自检从 9 条涨到 28 条，却因为丢了两条被连拒三次。"

改成"每丢 1 条至少多过 3 条"后，31 次修复公开分零下降。

对照我们：修复规则是"验收失败 → 整个文件重发 → 再失败 → 再重发"，没有接受
规则，也没有丢分守卫。`repair` 阶段吃掉 79%（keep）到 100%（stackoverflow）的请求。

**③ 确定性旧行为守卫，不调模型。**

- 起草前在隔离副本上以未登录状态遍历起点应用**两遍、取交集**作基线；
- 之后每个版本按原路径重放，基线项丢了就交修复并**否决该改动**；
- 需求写明的改名、删除豁免。

读数：合成破坏 **8/8 检出**；练习 6 题升级产物上 **134 项发现，132 项是真实的
可见界面回归**，噪声 2/6 = 0.33 项/应用。在 12306、BookStack、PrestaShop 上
分别找回 45、24、161 项旧界面。

对照我们：我们有 `.arc-good` 回退链，但那是"交付最后过检态"，不是"检测旧行为
是否被破坏"。前者保底，后者防退化——两件不同的事。

**④ 实验纪律：116 条实验，42 条按读数砍掉。**

`EXPERIMENTS.md` 每一行有：假设、做法、**事先写死的判据**、结果读数、
结论（保留/撤回/证伪/不采用/仅诊断）、证据链接。

42 条是**按判据砍掉的**，包括一些"看起来能涨"的：

| 候选 | 读数 | 判据 | 结论 |
| --- | --- | --- | --- |
| 4.21 Sheet 批次 | Sheet 69 | 78 | 撤回 |
| 4.23 换套测试再修 | 82 · 56 · 78，均值 72 | ≥ 77 | 关闭 |
| 只起草、多抽样 | S 40.5 | 当时 57.4 | 撤回 |
| 双初稿择优 | GitHub 16 | ≥ 17 | 撤回 |
| 决赛候选五 | 最好 47/60 | > 50/60 | 撤回（删除提交） |
| v7 | S 110.25 | 按 S | 撤回（删除提交，v6 恢复） |

对照我们：台账 39 行，有"下一步"，但**没有事前写死的判据**。结果是每次改动后
都能找到理由说"这次不算数，下次会好"。

### 2.2 Limitless / arc_pi —— 把"不调模型的检查"用到极致

仓库：[Simonghj/arc_pi_r6](https://github.com/Simonghj/arc_pi_r6)

架构是 Python 编排 + Pi agent 引擎（Node 子进程）。两个循环：

```
构建循环（每批需求一次）：需求 → 起草 → build → 契约检查 → commit → 下一批
测试+修复循环（全量）：写场景测试 → 真实浏览器验证 → 有界修复 ≤3 轮 → 交付最佳快照
```

**最值得学的是"契约检查"——它不调模型。**

> **契约检查**：不调用模型。需求文本中每个带引号的名称都必须出现在源码中，
> 每个反引号标注的 GIVEN 值都必须由后端创建。有缺漏 → 发送一次列出缺漏的跟进提示。

这一条同时解决三个问题：

1. **零成本**：不烧 token，毫秒级；
2. **确定性**：不依赖模型理解，不会幻觉；
3. **早失败**：build 之后立刻跑，不用等浏览器验收。

对照我们：`aria_lint` 走的是**生成 Playwright spec 跑 DOM** 的路线——要起服务、
要跑浏览器、每节点 1200 秒量级。方向对，但重了一个数量级。而且只覆盖
"role + 可访问名"，没覆盖"引号消息串"和"反引号 GIVEN 种子值"。

其他关键机制：

| 机制 | 读数/说明 |
| --- | --- |
| **项目地图** | 每批前列出每个源文件的导出、API 路由、页面路由，**不调模型**。智能体不必自己搜索文件。 |
| **每次改动后 build** | 构建失败 → 带错误的修复提示；回复截断 → 续写提示；没有改动 → 一次催促。 |
| **新会话交接** | 上下文用超 80% 时写交接笔记（已实现 id、文件地图、数据模型、种子、API、NEXT BATCH），新会话从笔记继续。 |
| **测试绕过 UI 就删掉** | 直接访问 URL、调 API、CSS 选择器、读存储的 spec 全部删除——保证测试走真实 UI。 |
| **验证口径** | 全新构建、1 worker、不重试、每测试 10 秒。 |
| **修复接受规则** | 每轮：**接受**（修好构建/启动或多过测试 → 新快照）/ **保留**（没丢测试，不更新快照）/ **回退**（丢测试）。 |

注意最后一条：他们也有"保留"这个中间态。丢测试不一定回退，但**不会更新最佳快照**。
这比我们的"要么过要么重发"细得多。

### 2.3 OpenCollab —— 把"协作是否真的发生"变成可测量的量

仓库：[RISE-X-Lab/OpenCollab](https://github.com/RISE-X-Lab/OpenCollab)

第 1 名。贡献不在"多智能体"这个想法本身，而在**证明协作是否真的发生**。

他们发现一个现象，叫 **illusion of collaboration（协作的幻觉）**：

> "在 OpenCollab 的 trace 里，它们经常没有真的协作：lead agent 向队友交代了任务，
> 然后自己把活干了；或者在交接之前就花光了整个 token 预算。声明出来的团队
> 塌缩成了单个 agent。"

于是他们把这件事变成可测量的指标：**Adherence**（遵从度）= 真正按声明组织的
运行占比。同一套团队配置，只改一个设置：

| 对参考团队的改动 | Adherence |
| --- | ---: |
| 无（Qwen3.8-Flash，开放提示，全部工具，星型拓扑） | 47.2% |
| 提示让交接变成强制 | 91.7% |
| **lead agent 只给只读工具** | **94.4%** |
| 每个角色都用 GPT-5.6-Luna | 97.2% |

**"lead agent 只给只读工具"这一条，把遵从度从 47.2% 拉到 94.4%**——因为 lead
没法自己干活，只能真的委派。

这对我们有一个直接启示，虽然我们不是多智能体架构：**如果你想让某个行为发生，
就让它成为唯一可行的路径，而不是写在提示词里请求它。**

其他机制：

| 机制 | 说明 |
| --- | --- |
| **规则在调用时强制执行** | 沿未声明边的消息被拒绝并记录；每个 agent 的 token 预算在**每次模型调用前**检查。 |
| **事件流而不是散文日志** | `--trace` 每步一条 JSONL，带 run / agent / role / event type / token usage。脚本可重建"谁做了什么"，不用解析聊天记录。 |
| **隔离工作区** | 队友在自己的 git worktree 里干活，交回 diff。 |
| **Weave 工作流** | 有序的组，每组在新会话里跑，共享同一工作区；**可执行的检查**提供交接证据并决定交付是否通过；失败检查触发**有界**的修复会话序列。 |
| **7 个受控比较条件** | 模型、工具、预算、上下文、拓扑可在运行前显式设定；Realized 和 Compared 可在运行后检查。 |

他们还做了一张审计表：十个 agent 工件（AutoGen、AG2、LangGraph、SWE-agent、
OpenHands、Claude Code、Codex CLI、DeepSeek Harness、Inspect AI、HAL）在七个
条件上的表现——只有 OpenCollab 全部 ✓。这个做法本身值得学：**把自己的系统
放进同一张表里被审计**。

## 三、逐项对照：七个分岔

把三支队伍和我们放在一起，差距收敛成七个具体分岔点。每一条都有我们的读数
和他们的读数。

### 分岔 1 · 起草：多轮工具循环 vs 一次调用

| | 我们 | VOLO |
| --- | --- | --- |
| 做法 | 逐节点：实现 → 验收 → 修复 → 再验收，节点内多轮工具调用 | 需求 + 方言卡 + 旧源码 → **一个请求**，温度 0 |
| keep 读数 | 161 req / prompt 5.41M / $0.91 / 68min（32/32） | 186 calls / ¥12.03（22/32）→ **一次调用 27/32、29/32，¥0.88–0.94** |
| stackoverflow | **1331 req，100% 全是 repair**，prompt 65.4M，$9.30 | — |

我们的成本结构（台账 #0，keep 32 节点）：

```
repair    127 请求（79%）  prompt 4.96M（92%）  completion 190K
implement  34 请求         prompt 0.45M          completion 363K（65%）
```

**79% 的请求在修复，92% 的 prompt token 在修复。** 而修复修的是"上一轮实现没做对
的东西"。VOLO 的结论：与其修，不如一次做对——质量更高（29/32 vs 22/32），
成本低 13 倍。

T2 stackoverflow 更极端：1331 个请求 **100% 全是 repair**，prompt 65.4M，中位数
上下文 106K chars。上下文越滚越大，模型在巨大的会话里做小步挪动，收敛慢且容易
改坏别处。

### 分岔 2 · 验收：DOM 存在性 vs 四层检查

| 层 | 我们 | 他们 |
| --- | --- | --- |
| **源码级契约**（不调模型） | ❌ 没有 | ✅ arc_pi：引号名必须在源码、反引号 GIVEN 必须在种子 |
| **需求驱动的行为测试** | ⚠️ 有代理套件，但**不进平台包** | ✅ VOLO：同一模型只读需求写测试，**接进修复环** |
| **旧行为守卫**（不调模型） | ❌ 没有 | ✅ VOLO：双 pass 取交集，8/8 合成破坏检出 |
| **可访问名 lint** | ✅ `aria_lint`（起服务跑 DOM） | — |

我们的验收信号停在"存在性"：DOM 里有没有 `role=grid` 且 `aria-label="Worksheet grid"`。
它测不出：

- 点了 Import CSV 之后对话框里有没有正确字段
- 排序之后行序对不对
- 公式算出来的值对不对

代价是**一次 25 倍的幻觉**：

| 运行 | harness 判定 | 代理测试判定 |
| --- | ---: | ---: |
| `real-sheet-baseline-0` | **19/24 ATOMIC PASSED** | **1/28（4%）** |

我们在 `06` 里写下了这个数字，但当时没有意识到它意味着什么：**harness 说 19/24
过了，真实水位是 4%。** 后续所有"本地全绿"的结论都要打这个折扣。

### 分岔 3 · 修复：无界整文件重发 vs 有界定点编辑

| | 我们 | VOLO | arc_pi | OpenCollab |
| --- | --- | --- | --- | --- |
| 编辑形态 | 整文件重写 | SEARCH/REPLACE 定点 | 定点编辑 | 原生编辑 + 补丁 |
| 接受规则 | 验收过了就留 | **每丢 1 条至少多过 3 条** | 接受 / 保留 / 回退三态 | 有界 + 证据比较 |
| 上限 | 5 轮（`repair_rounds`） | **24 次调用 / ¥10 / 连续 4 次丢弃** | **3 轮** | **3 轮 × 60 步 × 600s × 2M token** |
| 停滞检测 | 停摆刀（连续 2 轮签名不动） | — | 2 轮无进展即停 | 2 轮无可观测进展即停 |

我们的 `repair_rounds = 5` 听起来有界，但每一轮是**整文件重发**。keep 的单文件
前端到后期 50-60K chars，每轮重发整个文件。stackoverflow 的中位数上下文 106K。

VOLO 的读数：整份重发大文件每轮弄坏约 10 条；定点编辑让同一份初稿从 25 到 38。

### 分岔 4 · 知识载体：散文提示词 vs 阶梯

| 载体 | 我们 | VOLO |
| --- | --- | --- |
| 门禁（代码检查） | `aria_lint`（1 类） | 引号词门禁、地标门禁、路由名门禁、js 语法检查、资产洞探针、种子金丝雀…… |
| 脚手架原语 | `template/`（基础） | `oneshot/scaffold/`：布局、路由、存储、对话框、通知、后端守护 |
| 从需求算出来的表 | 种子清单（部分） | 种子清单带编号前置、位置声明表 |
| 散文规则 | **13KB 的 `pipeline-implement.md`** | **59 行的方言卡**（最后一级） |

VOLO 的消融支撑这条：把卡片里"题目形状"的规则删掉（`exp/generic-card`），
六题均值从 65.2/58.7 掉到 55.3/45.7——说明**规则该在门禁和脚手架里，不在散文里**。

我们的 13KB 提示词里有多少"本该做成门禁但写成了散文"？赛后回看，至少这几类：

- 绝对路径规则（`src="/app.js"`）→ 应该是资产洞探针（我们后来做了）
- 隐藏元素必须从 DOM 移除（`[hidden]` 被 `display:flex` 覆盖）→ 应该是 CSS 检查
- 每个断言词恰好挂在一个独立元素上 → 应该是 DOM 结构 lint
- 种子数据逐字预置 → 应该是契约检查（arc_pi 的做法）

### 分岔 5 · 实验纪律：台账 vs 判据

| | 我们 | VOLO |
| --- | --- | --- |
| 记录量 | 39 行台账 | **116 条实验** |
| 事前判据 | ❌ 多数没有 | ✅ 每行都有"判据（事先写死的）" |
| 按判据砍掉 | 少数 | **42 条** |
| 单样本 vs 配对 | 多为单样本 | 09-23 起强制配对六题样本 |

VOLO 在 09-23 做的这个决定，我认为是他们整届最重要的一个：

> "23 个独立样本没有一个满分，相邻两版差 5 到 8 分，落在噪声里。我们停掉单样本
> 迭代，改成每个机制先写死判据再上场。"

他们还算过分辨力：单样本对单样本只能分辨 **24–32 个百分点以上**的差异。

我们的台账里很多结论建立在单样本上。比如"某刀有效，62 → 77"，可能有一半是噪声。

### 分岔 6 · 交付：回退链 vs 永不交付空

| | 我们 | 他们 |
| --- | --- | --- |
| 机制 | `.arc-good`（最后过检快照）+ `.arc-best`（全量回归快照）+ 渐进交付 | VOLO：**永不交付空**；任何异常后交付最后一个完整版本 |
| 事故 | arch-6：collect 只认 `.arc-best`，墙掐跑走不到全量回归 → 交付半成品 + 脏 store → **7/100** | 截断与断流曾让整题零分 → 改成"永不交付空" |

我们后来修了（collect 回退链补 `.arc-good`），但这是**补漏**，不是原则。
VOLO 把它写成第一原则，所以在截断、断流、网关故障、回退模型切换所有路径上
都覆盖了。

### 分岔 7 · 成本观：事后刹车 vs 架构选择

| | 我们 | VOLO |
| --- | --- | --- |
| 单跑最高 | **¥104.8**（github-arch-0，8h，220M token） | 决赛两题合计 **¥2.56** |
| sheet 单题 | ¥49（41 分） | 初赛两题 ¥6.35（166 分） |
| 成本控制 | 停摆刀 + 燃料表（**10-01 才落地**） | 一次起草（09-15）+ 有界修复（09-23）+ 缓存前缀（09-27） |

我们的成本控制是**事后刹车**：先跑，跑贵了，再加闸。他们的是**架构选择**：
一次起草天然便宜，有界修复天然有界。

而且我们直到 10-02 才明确写下这句话：`S = p·(B/b)^0.2` 里 b 是弱惩罚（b 翻倍
S×0.87），p 是线性主导（p 翻倍 S×2）。**在 p 很低的时候，任何成本优化都是次要的。**
我们花了大量时间优化 b。

## 四、我们错在哪（按影响排序，每条带代价）

### 错误 1 · 把"多轮工具修复"当成主路径

**证据**：keep 79% 请求在 repair；stackoverflow **100%** 请求在 repair，prompt 65.4M。

**代价**：单题成本 ¥49–104，VOLO 两题 ¥6.35。**每分成本差 31 倍。**

**为什么难改**：我们的内核（`octos-pipeline`）就是围绕"实现节点 + 验收节点 +
失败回边"建的。改起草方式等于换架构。但 VOLO 在 09-15 就做了这个决定，
那时离正式赛还有 9 天。

**根因**：我们把"修复能力"当成了核心竞争力，而它其实是**实现能力不足的补偿**。
补偿越强，越不容易发现根本问题是"一次没做对"。

### 错误 2 · 验收信号停在存在性，且代理测试不进环

**证据**：`real-sheet-baseline-0` harness 19/24 vs 代理 1/28（4%），**25 倍幻觉**。

**代价**：09-24 到 09-29 之间所有"本地全绿"的结论都不可信。我们在错误的地图上
找了五天的路。

**为什么难改**：代理套件（github 44 spec + sheet 24 spec）是"保密"的——不进平台包、
不进 agent 工作区。这在合规上是对的（避免测试泄漏），但在工程上是致命的：
**它只能做事后裁判，不能驱动修复**。

VOLO 和 arc_pi 的解法是：让**同一个模型**只读需求写测试，所以测试天然可以进包、
进环，且不泄漏任何隐藏信息。

**根因**：我们把"测试"理解成"评分工具"，他们理解成"反馈工具"。

### 错误 3 · 冷启动天花板误读成"墙不够长"

**证据**：09-30 我们把冷启天花板钉死在 25-26，结论是"墙是冷启抬升的唯一杠杆"，
于是 6h → 12h → 24h。

**代价**：¥65/12h 的双跑，只换来 +1-2 个节点。

**真实病因**：deepseek-v4-flash 在 6h 内建不完 24 个节点，因为每个节点都要走
"实现 → 验收 → 修复 → 再验收"的长链。VOLO 在同一模型上一次起草，单节点轮次
少一个数量级。

**根因**：我们测量的是"墙与节点的关系"，没有测量"节点内部的时间花在哪"。
如果当时统计一下 keep 的 repair/implement 时间比（28.5min vs 31.0min），
就会发现问题不在墙。

### 错误 4 · 最后 48 小时才切方向，没留验证时间

**证据**：10-02 才开始做 stage 拆分、视觉语义入链、外聘 Agent 建产物。stage-1
本地做到 30/30、stage-2 29/29，但平台最后一票 **stage-2/3 零分**。

**代价**：github 16 分全部来自 stage-1。如果 stage-2/3 按本地水位兑现，
github 应该在 60+。

**根因**：没有把"一次平台往返（4-12h）+ 一次回滚余量"算进截止时间。

**应该写下的规则**：

```
方向切换截止 = 比赛截止 − 2 × 一次完整平台往返 − 1 次回滚余量
```

### 错误 5 · 多变量同时上车，归因失效

**证据**：台账 #9「D3.2 + E1 + E3 联合腿」、#10「上游合并 + D3.x 移植」、
#19/#20「R3 四刀 + 绝对路径 + 烟雾测试全上」。

**代价**：当 #9 结果是 1/28 时，无法判断是哪一项造成的。整个 09-26 的迭代
因此效率极低。

**对比**：VOLO 的 116 条实验里，只有标为消融的几组是一次只改一处，其余都在
文档里**明确标注"改动常打包上场"**——他们承认局限，我们假装没有。

**根因**：时间压力下反复违反自己写下的"一次只改一处"。

### 错误 6 · 成本控制来得太晚，且优化错了对象

**证据**：停摆刀 + 燃料表 10-01 落地，比赛 10-03 结束。计分公式
`S = p·(B/b)^0.2`，p 线性主导，b 弱惩罚。

**代价**：最后两天的一部分时间花在了 b 上，而 p 才是主战场。

**根因**：没有在开赛第一天算清楚"p 和 b 的边际汇率"。

### 错误 7 · 没有事前判据，导致"永远差一点"

**证据**：39 行台账里，"下一步"很多，"判据"几乎没有。

**代价**：每次改动后都能找到理由说"这次不算数"。整个比赛没有一条机制被明确
判死并删除。

**对比**：VOLO 砍掉 42 条，包括"决赛候选五 47/60（判据 50/60）"和"v7 S 110.25
（不如 v6 S 120.49）"——**已经能拿高分的版本也被删掉**。

## 五、他们对在哪（六条可迁移的原则）

### 1. 一次做对 > 反复修对

**读数**：VOLO 多轮 22/32 ¥12 vs 一次 29/32 ¥0.9。**质量更高，成本低 13 倍。**

**为什么**：多轮修复的每一轮都在重发整个上下文（我们实测 90-106K chars/请求），
模型在巨大上下文里做小步挪动，收敛慢且容易改坏别处。一次起草把所有信息压进
一个请求，模型看到的是完整任务。

**可迁移**：任何"生成 + 验证 + 修复"的循环，先问"能不能一次生成对"。

### 2. 能做成门禁的，不要写进提示词

**读数**：VOLO 的消融——删掉卡片里题目形状规则，六题均值 65.2/58.7 → 55.3/45.7。

**分级**：

```
门禁（代码检查 + 有界修复） > 脚手架原语 > 从需求算出来的表 > 散文规则
```

**可迁移**：每次想往提示词里加一条规则，先问"能不能写成检查"。

### 3. 测试是反馈工具，不是评分工具

**读数**：VOLO 自写测试接进修复环后 Sheet 43 → 53 → 79。我们的代理测试不进环，
只能做事后裁判。

**关键设计**：让**同一个模型**只读需求写测试——测试天然可进包、不泄漏隐藏信息、
且和实现共享同一套需求理解（虽然这带来"共享误读"的风险，见局限）。

**可迁移**：如果测试不能驱动修复，它就只是评分。

### 4. 判据先写，再跑

**读数**：VOLO 23 个样本 0 满分，相邻版本差 5-8 分 = 噪声。于是停掉单样本迭代。

**规则**：每个机制上场前写下：假设、判据、读数、去留。读数不达判据就撤，不解释。

**可迁移**：单样本对单样本只能分辨 24-32 个百分点以上的差异（VOLO 的估计）。
改动预期提升小于这个数，就需要配对样本，或者不要做。

### 5. 让行为成为唯一可行路径，而不是请求它

**读数**：OpenCollab 的 Adherence——只把 lead agent 的工具改成只读，遵从度从
47.2% 到 94.4%。

**为什么**：lead 没法自己干活，只能真的委派。

**可迁移**：任何"希望模型这样做"的需求，先问"能不能让它不做就失败"。
提示词是请求，门禁是强制。

### 6. 永不交付空

**读数**：VOLO 截断与断流曾让整题零分 → 改成"任何异常后交付最后一个完整版本"。

**可迁移**：交付路径上每一条异常分支都要有"至少交付什么"的答案。

## 六、为什么我们没有走到那条路（归因）

这一节写给下一届的自己。不是找借口，是找**可修正的决策模式**。

### 1. 我们被"官方模板"锚定了

我们用的是 `octos-arc`——官方团队的参赛版。它有完整的骨架：DAG、节点、验收、
修复回边。这套架构是"官方推荐"，所以我们默认它是对的。

但官方模板本身也是**一个参赛方案**，不是最优解。VOLO 和 arc_pi 都是自建
harness，从零选择架构。他们没有被锚定。

**教训**：拿一个成熟框架当起点是优势（省时间），但要定期问"这个框架的核心假设
还成立吗"。我们的核心假设是"逐节点修复能收敛"，它在弱模型上不成立。

### 2. 我们把"机制数量"当成了进展

39 行台账里，机制一条一条加：D3、C1a、R1、R2、R3、R4、E1、E3、A19、A20……
每条都有尸检、有读数、有代码。看起来非常扎实。

但这些机制大多是**在错误的主路径上打补丁**。主路径是"多轮修复"，所有机制都在
让它更高效一点。而 VOLO 做的是**换主路径**。

**教训**：机制数量是虚荣指标。真正的问题是"主路径对不对"。

### 3. 我们过早优化了成本

¥65/12h 的尸检让我们非常难受，于是做了停摆刀和燃料表。这两个机制本身很好
（VOLO 也有类似的"2 轮无进展即停"）。

但我们在 p 只有 25-41 的时候，把注意力放在了 b 上。而 p 翻倍 S 翻倍，b 减半
S 只 ×1.15。

**算一下边际汇率**：`S = p·(B/b)^0.2`

```
∂S/∂p = S/p
∂S/∂b = -0.2·S/b
```

在 p=25、b=¥49 时：一个通过率点的价值 = `S/25`，一元钱的价值 = `0.2S/49`。
两者相除：**一个点 ≈ 10 元**。

所以任何花不到 10 元能换一个点的改动都值得做；任何省不到 10 元却损失一个点的
改动都不值得。

**教训**：先算边际汇率，再决定优化什么。

### 4. 我们没有把"本地全绿"当成一个需要验证的假设

`real-sheet-baseline-0` 的 19/24 vs 1/28 是 09-24 就发现的。我们记录了它，
但没有因此改变方法。后续仍然用 harness 的 PASSED 作为进展信号。

**教训**：当一个测量结果和另一个测量结果差 25 倍时，**先修测量，再修被测对象**。
我们反过来了。

### 5. 我们太晚才读对手

比赛期间我们读的是官方文档、需求、平台规则。赛后读三个头部仓库，发现他们的
关键决策（一次起草、自写测试、3:1 规则）都在 09-15 到 09-25 之间就做了。

**教训**：开源比赛的对手仓库是公开情报。开赛第一周就该读，不是赛后。

## 七、如果重来一次（可执行清单）

按投入产出排序。前三条我认为能单独把分数抬到 70+。

### 第 1 周就要做的（架构级）

**① 把起草改成一次调用**

- 需求节点 + 已实现源码 + 种子清单 + 方言卡，压进**一个请求**，温度 0；
- 只输出改动或新增的完整文件；截断就续写；
- 用 `OCTOS_ARC_INLINE_SOURCE_CHARS` 控制内联量（我们已验证 15000 比 40000
  省 35% token，方向对，但还在多轮框架里）。

**预期**：单节点成本降一个数量级，首过率上升。

**② 源码级契约检查，不调模型**

把 `aria_lint.py` 从"生成 Playwright spec 跑 DOM"改成"扫源码文本"：

- 需求里每个 `引号名字` 必须作为字符串出现在 `frontend/src/**`；
- 每个 GIVEN 反引号值必须出现在 `backend/seed-default.json`（或 seed 函数）；
- 每个 THEN 引号消息必须出现在源码里。

失败直接喂修复轮。零 LLM 成本、零浏览器、毫秒级。

**③ 自写测试接进修复环**

- 平台跑里，`main.py` 用**同一个模型**只读需求生成 spec（不看应用）；
- spec 进 `verify_node.py` 的验收命令；
- 修复轮以 spec 失败为信号；
- spec 自身报错（编译/选择器）记为 error，不驱动修复；
- 绕过 UI 的 spec（直接 URL、调 API、CSS 选择器）删掉。

### 第 2 周做的（机制级）

**④ 有界修复 + 3:1 接受规则**

- 只许定点编辑（SEARCH/REPLACE），禁止整文件重发；
- 每次修复后重跑全量 spec，**每丢 1 条至少多过 3 条**才接受，否则回滚；
- 连续 N 次被拒 / 预算耗尽即停，交付最后一个完整版本。

**⑤ 确定性旧行为守卫**

- 起草前在隔离副本上遍历起点应用两遍、取交集作基线；
- 每个版本按原路径重放，基线项丢了就否决该改动；
- 需求写明的改名/删除豁免。

**⑥ 知识下沉**

把 13KB 提示词逐条分类：能写成门禁的写成门禁，能进脚手架的进脚手架，
剩下才是方言卡。目标：卡片 ≤ 60 行。

### 贯穿全程的（纪律级）

**⑦ 判据前置**

每个机制上场前写下：假设、判据、读数、去留。读数不达判据就撤，不解释。
**已经能拿高分的版本也要按判据删。**

**⑧ 一次只改一处**

时间压力下最容易违反，所以要机制化：每次提交只允许一个机制 diff，多机制
改动必须拆成多个候选，分别读数。

**⑨ 方向切换截止时间**

```
切换截止 = 比赛截止 − 2 × 一次完整平台往返（4-12h） − 1 次回滚余量
```

过了这个点只做参数调整，不做架构变更。

**⑩ 开赛第一周读对手仓库**

三个头部仓库在 09-15 到 09-25 之间就做了关键决策。这些是公开情报。

## 九、诚实的局限

写在这里，是因为下一届还会有人踩同样的坑。

1. **很多结论只有一两个读数。** 单跑方差很大（同一个包 sheet 在 62 附近抖动，
   github 在 0-5 之间跳）。我们的"某刀有效"多数是单样本对单样本。
   VOLO 估计单样本只能分辨 24-32 个百分点的差异。
2. **本地分来自代理裁判，不是官方。** 我们自己的分析显示代理套件偏乐观
   （同一产物本地 97、平台 41）。任何"本地满分"的结论都要打折。
3. **平台分也受外部变化影响。** 09-24 发错题、09-25 套件修复、需求两次改版，
   都混进了成绩曲线。VOLO 也遇到同样的事（10-02 主办方更新 GitHub 需求，
   同一提交 GitHub 从 18 到 46），他们明确写了"这一跳不能算我们的功劳"。
4. **改动常打包上场。** 见错误 5。
5. **我们从未拿到平台的逐测试明细。** 只有总通过率，归因只能靠本地复现。
   这是这次最大的信息劣势，也是头部队伍用"自写测试"绕开的点。
6. **"42/16" 是最终入账，不是我们的能力上限。** 本地隔离尺 62/51 说明产物本身
   比平台分好；但比赛只看平台分。
7. **对三支队伍的分析基于他们公开的文档，不是内部过程。** 他们也可能有大量
   未公开的失败与回撤。VOLO 的 116 条实验和 42 条砍掉是公开的，这值得敬佩；
   我们只能看到这一面。

## 十、一句话

> 我们造了一台能自我诊断的机器，却没来得及让它一次就把事情做对。

机制、尸检、实验纪律都立住了；输在**实现路径的选择**——用多轮修复去弥补
一次实现的不完整，而这条路在弱模型上成本超线性、收敛不可靠。

三支头部队伍用同一个模型，证明了差距不在模型，在 harness。他们的共同选择是：

- **一次做对**（VOLO 一次起草，29/32 ¥0.9）
- **确定性检查**（arc_pi 契约检查不调模型，VOLO 守卫 8/8 检出）
- **测试驱动修复**（VOLO 自写测试接环，Sheet 43 → 79）
- **判据前置**（VOLO 116 条实验砍掉 42 条）
- **让行为成为唯一路径**（OpenCollab 只读工具让 Adherence 47.2% → 94.4%）

下次把顺序倒过来：**先保证一次做对，再谈怎么修。**
