### 一个必须先说的判断

三支队伍不是"同一套方案的三次实现"。他们走了三条不同的路：

| 队伍 | 参赛配置 | 核心押注 | 名次 |
| --- | --- | --- | --- |
| **OpenCollab** | **Weave 工作流 + Single2 单 agent**（串行、每单元新会话） | **上下文切分 + 可执行检查** | 第 1 |
| **VOLO** | 单 agent 一次起草 + 有界修复 | **减法**（少调用、少上下文、少修复） | 第 2 |
| **arc_pi** | Python 编排 + Pi agent 引擎 | **确定性检查**（不调模型的门禁） | 决赛队伍 |

> ### ⚠️ 一个必须先纠正的误读：第一名**不是**"多 agent 架构"
>
> OpenCollab 的仓库叫"多智能体框架"，所以很容易以为它靠多 agent 协作赢。**不是。**
>
> 他们的 ARC-Bench 提交用的是 **Weave 工作流**，配置是 `agent_profile="single2"`
> （见 `examples/arcbench-evolution-r6/main.py`）——**同一个单 agent 实例，串行跑
> 多个工作单元，每个单元开新会话**。README 的原文：
>
> > "The core workflow schedules independent **Single2 instances** over one application
> > workspace. Each requirement group and repair round has a **fresh conversation**."
>
> 而他们那个真正的多 agent 模式（**Team** 控制器）恰恰是他们自己在论文里批评的
> 东西——见 [2.3 节](#23-opencollab--第一名靠的是上下文切分不是多-agent)。
> Team 模式下 **47.2% 的运行里协作根本没发生**：lead 给队友交代完任务，然后自己
> 把活干了，briefing 的 token 白烧。
>
> 所以"多 agent 更费 token"这个直觉是**对的**，但它描述的是 Team 模式；
> **第一名用的是单 agent + 新会话**，省 token 的原理见 [2.3 节](#23-opencollab--第一名靠的是上下文切分不是多-agent)。

三支队伍的共同点：**都在做减法，而不是加机制**。而 OpenCollab 和 VOLO 虽然拓扑
完全不同（前者多单元串行、后者一次调用），收敛到了**同一个原理**：
**别让上下文无限增长。**

而我们整个比赛期间在**加机制**——39 行台账，39 次加法。

## 二、三支队伍各做对了什么

### 2.1 VOLO-AI —— 减法做得最狠的一支

#### 起点与我们几乎一样

> "VOLO Factory 是一个多轮工具循环……可一换成 Keep 这样的大题，一局要一百多次
> 调用、八到十二块钱，最好也只有 25/32。"

> "同一道 Keep：多轮循环跑了 186 次调用，22/32、12.03 元；**一次调用加一张
> 『方言卡』，27/32 和 29/32，每次不到 1 元**。当天刚定下的 TypeScript 内核重写
> 和 Prime Agent 适配一起停掉，入口只剩一次起草。"

这就是我们的起点：多轮工具循环、逐节点自检修复、大题成本爆炸。区别是他们在
**09-15**（比赛开始前 9 天）做了这个减法，我们整个比赛期间都没做。

#### 最终四步

| 步骤 | 进入架构 | 做什么 | 源码位置 |
| --- | --- | --- | --- |
| **一次起草** | 09-15 | 需求 + 方言卡 + 旧源码 → **一个请求**，温度 0 | `oneshot/main.py: draft_messages()` / `draft_application()` |
| **自写测试** | 09-25 | 同一模型**看不到应用**，只读需求写 Playwright 测试 | `oneshot/testgen.py` |
| **有界修复** | 09-23 | SEARCH/REPLACE 定点编辑 + 3:1 接受规则 | `oneshot/main.py: parse_repair()` / `_apply_hunk()` |
| **守卫交付** | 10-06 | **不调模型**：重放旧行为 + 核对需求写明的位置 | `oneshot/regression_guard.py` |

#### 机制 ① 知识阶梯（ADR 0001）

他们把所有失败族按"最低能承载它的载体"分层：

```
门禁（代码检查 + 有界修复）  >  随包发布的脚手架原语  >  从需求算出来的表  >  提示词里的散文规则
        ↑ 优先                                                              ↓ 最后手段
```

ADR 原文：

> "Every failure family is addressed at the lowest carrier that can hold it, in
> this order: gate (code check + bounded repair) → scaffold primitive shipped
> with the package → table computed from the requirement and prepended to the
> prompt → prose rule in the card. **A prose rule is the last resort, not the first.**"

支撑这条的消融读数（`EXPERIMENTS.md` r16 消融）：把卡片里"题目形状"的规则删掉
（`exp/generic-card`），六题均值从 65.2 / 58.7 掉到 55.3 / 45.7——**说明规则
该在门禁和脚手架里，不在散文里**。

#### 机制 ② 3:1 修复接受规则

原来的规则是"只增不减"（修复不能丢测试）。读数推翻了它：

> "修好路由的修复让自检从 9 条涨到 28 条，却因为丢了两条被连拒三次。"

改成"每丢 1 条至少多过 3 条"后，**31 次修复公开分零下降**。

源码常量（`oneshot/main.py`）：

```python
REPAIR_CALLS = 24        # Completed repair calls, bounded independently from the draft.
REPAIR_CNY = 10.0        # Repair spend per task in CNY
REPAIR_REJECTIONS = 4    # Consecutive discarded repairs before stopping the search.
REPAIR_SHOWN = 40        # Failing scenarios listed in one repair request.
LOSS_RATIO = 3           # A repair that loses passing scenarios is kept only when it gains this many per loss.
REPAIR_SECONDS = 3 * 3600  # No repair round starts after this much time in the repair phase.
```

注意这五个常量**互相独立**：调用数、花费、连续被拒次数、时间、失败列表长度。
任何一维触发即停。这是"有界"的完整含义。

#### 机制 ③ 确定性守卫（不调模型）

- 起草前在隔离副本上以未登录状态遍历起点应用**两遍、取交集**作基线；
- 之后每个版本按原路径重放，基线项丢了就交修复并**否决该改动**；
- 需求写明的改名、删除豁免。

| --- | --- |
| 合成破坏检出 | **8/8** |

| 练习 6 题升级产物发现 | **134 项，132 项真回归**，噪声 2（0.33 项/应用） |
| 找回旧界面 | 12306: 45 项 / BookStack: 24 项 / PrestaShop: 161 项 |

**守卫的接受规则比 3:1 更硬**（报告第 4 节）：

> 1. 上一保留版本仍保有、候选现已丢失的任一基线项，**直接拒绝**，新需求增加多少

> 2. 需求合理豁免的项不参与这条否决。

### 2.2 Limitless / arc_pi —— 把"不调模型的检查"用到极致

#### 两个循环

```
构建循环（每批需求一次）：需求 → 起草 → build → 契约检查 → commit → 下一批
测试+修复循环（全量）：写场景测试 → 真实浏览器验证 → 有界修复 ≤3 轮 → 交付最佳快照
```

#### 机制 ① 契约检查：不调模型

`arc_pi/contract.py` 的核心（我读过全文，这是真实实现，不是概念）：

```python
QUOTED_RE  = re.compile(r'[\u201c"]([^"\u201d\n]{2,60})[\u201d"]')  # “Name” / "Name"
BACKTICK_RE = re.compile(r"`([^`\n]{2,60})`")                     # `seed`
# A value the scenario itself creates; seeding it would break the create scenario.
TRANSIENT_RE = re.compile(r"does not (?:yet )?exist|not yet (?:used|exist)|\bunused\b|candidate|"
                          r"attempted|\btarget\b|\bnew\b", re.I)
INPUT_LIKE_RE = re.compile(r"^[a-z0-9]+(?:-[a-z0-9]+)+$")

def contract_notes(output: Path, nodes: list[dict]) -> list[str]:
    """Quoted names and existing seed records that appear nowhere in the source."""
    source = source_text(output)
    backend = source + " " + _joined(data_files(output))
    notes = [f'- name "{name}" is not rendered anywhere' for name in ui_names(nodes)
             if name not in source]
    notes += [f"- seed record `{value}` is not created by the backend" for value in seed_values(nodes)
              if value not in backend]
    return notes[:MAX_NOTES]
```

三个设计细节值得学：

1. **区分"UI 名"与"示例输入"**：`_is_ui_name()` 排除了邮箱、密码、slug、范围值、
   占位符——否则需求里的 `alice@example.test` 会被当成必须渲染的控件名。
2. **区分"种子"与"待创建"**：`TRANSIENT_RE` 让 "a user that does not yet exist"
   这句话里的所有反引号值都不进种子检查——**否则种了创建目标，创建场景就永远过不了**。
3. **`MAX_NOTES = 30`**：缺漏列表有上限，不会把提示词撑爆。

这套检查**零 LLM 成本、零浏览器、毫秒级**，在 build 之后立刻跑。

#### 机制 ② 项目地图

> 每批开始前，框架会列出每个源文件及其导出、API 路由和页面路由，智能体不必自己
> 搜索文件。**不调用模型。**

这是一个被低估的机制：它把"模型花 3-4 轮去 glob/grep/read 找文件"的成本，
换成了**一次确定性的文件扫描**。

#### 机制 ③ 修复三态

`arc_pi/runner.py` 的 `_repair_accepted()`：

```python
def _repair_accepted(best: dict, candidate: dict) -> bool:
    """Keep a candidate that passes more tests (or equal tests with fewer backend errors)."""
    if best.get("build") == "failed" and candidate.get("build") == "passed":
        return True
    if best.get("startup") == "failed" and candidate.get("startup") == "passed":
        return True
    best_passed = {t.get("id") for t in best.get("tests") or [] if t.get("status") == "passed"}
    candidate_passed = {t.get("id") for t in candidate.get("tests") or [] if t.get("status") == "passed"}
    if len(candidate_passed) <= len(best_passed):
        # Same tests still pass and the backend logs fewer errors: a real fix.
        return (best_passed <= candidate_passed
                and len(candidate.get("serverErrors") or []) < len(best.get("serverErrors") or []))
    return True  # net gain counts: e.g. 2 -> 5 passing was reverted when one old pass flipped
```

关键在最后一行注释：**净增就算数**。他们曾经因为"丢了一条旧的"而拒掉"2 → 5"的修复。
这和 VOLO 的 3:1 是同一类洞察：**拒绝规则过严会杀掉真正的改进**。

三态：**接受**（新快照）/ **保留**（没丢测试，不更新快照）/ **回退**（丢测试）。

#### 机制 ④ 测试绕过 UI 就删掉

> 绕过界面的测试（直接访问 URL、调用 API、CSS 选择器、存储）会被删除。

这条保证了"测试通过"和"用户能用"是同一件事。我们的代理套件没有这条纪律。

### 2.3 OpenCollab —— 第一名靠的是上下文切分，不是多 agent

#### 先看清它到底怎么跑的

OpenCollab 有两个控制器，差别极大：

| 控制器 | 是什么 | ARC-Bench 用了吗 |
| --- | --- | --- |
| **Team** | 多 agent 并发协作，YAML 声明角色/工具/预算/拓扑 | ❌ 没用 |
| **Workflow（Weave）** | 有序的工作组，**每组一个 fresh session**，共享同一 workspace | ✅ **决赛用的就是这个** |

`examples/arcbench-evolution-r6/main.py` 的调用参数是决定性证据：

```python
result = await client.workflow(
    weave,
    {...},
    agent_profile="single2",   # ← 单 agent 实现
    concurrency=1,             # ← 并发 1
    limit_mode="explicit",
    ...
)
```

而 `workflow.py` 里的装饰器写得明明白白：

```python
@workflow(
    name="arcbench-weave-r6",
    description="Independent Single2 instances implement requirement groups, "
                "verify and repair a shared application.",
    phases=["prepare", "implement", "verify", "repair", "deliver"],
)
```

**所以第一名是：一个单 agent，串行跑多个工作单元，每个单元开新会话。**

那它为什么叫"多智能体框架"？因为 Team 是它的研究重点（有 arXiv 论文），
但**比赛提交没用 Team**。这两件事必须分开看。

#### 为什么"每单元新会话"更省 token（而不是更费）

这是整篇复盘里最值得算清楚的一笔账。

设：
- `P` = 共享前缀（系统提示 + 项目地图 + 需求摘要），每次会话都一样；
- `C` = 单个工作单元的增量上下文；
- `N` = 工作单元数。

**一个长会话**（我们的做法）：第 k 个单元时上下文 ≈ `P + kC`

```
总 prompt = Σ(P + kC) = N·P + C·N(N+1)/2   →  O(N²)
```

**每单元新会话**（Weave 的做法）：每次上下文都是 `P + C`

```
总 prompt = N·(P + C)                       →  O(N)
```

而且 `P` 每次完全一致 → **前缀缓存命中**。按 VOLO 记录的网关价目
（`oneshot/main.py` 的 `PRICES`）：

| | deepseek-v4-flash |
| --- | ---: |
| 输入（未命中缓存） | 3.0 CNY / M |
| **输入（命中缓存）** | **0.1 CNY / M** |
| 输出 | 9.0 CNY / M |

**缓存命中比未命中便宜 30 倍。** 长会话里 `P` 只在前几轮便宜，后面全是新增的
`C`（未缓存）；新会话里 `P` **每一轮都是缓存命中**。

#### 我们就是反面样本

台账 #2（stackoverflow，T2 基线）的实测：

| 指标 | 读数 |
| --- | ---: |
| 总请求 | 1331 |
| repair 占比 | **100%** |
| 中位数上下文 | **106K chars** |
| >100K chars 的请求 | **1107 / 1331** |
| prompt tokens | **65.4M** |
| 花费 | **$9.30** |

会话越滚越大，模型在 100K+ 的上下文里做小步挪动——**既贵又笨**。这就是
`O(N²)` 的实际形状。

#### Weave 的具体配置（可对照）

`arcbench_r6/settings.py` 的默认值：

| 参数 | 值 | 含义 |
| --- | ---: | --- |
| `budget` | 16,000,000 | 总 token 预算 |
| `main_budget` / `main_hard_budget` | 12M / 14M | 主阶段软/硬上限 |
| `repair_reserve` | 2,000,000 | 预留给修复 |
| `max_steps` | 200 | 累计步数上限 |
| `wall_seconds` / `agent_seconds` | 6000 / 4800 | 100 min / 80 min |
| `max_output_tokens` | 32,768 | 单次输出上限 |
| `context_window` | 1,000,000 | 上下文窗口 |
| `max_repair_rounds` | 3 | 修复轮数 |
| `stagnant_round_limit` | 2 | **2 轮无进展即停** |
| `repair_steps` / `repair_timeout` | 60 / 600s | 每轮修复的步数与时间 |
| `group_check_fraction` | 0.25 | 每组检查占该组时间的比例 |

注意几个设计细节：

1. **`concurrency=1`**——串行。并发会争抢同一个 workspace，还要处理合并冲突。
   串行 + 每组新会话，把"并发复杂度"换成了"上下文干净"。
2. **`stagnant_round_limit=2`**——2 轮无可观测进展即停修复。和 VOLO 的
   `REPAIR_REJECTIONS = 4` 是同一类机制（数字不同，原理相同）。
3. **`group_check_fraction = 0.25`**——每组预留 25% 时间给检查。**检查时间是
   预算的一等公民**，不是"做完再看"。
4. **软预算可扩**（`extension_tokens = 1,000,000`）："Completed native edits and
   observed passing tests can support soft allowance extensions"——**只有真实
   产出才能解锁额外预算**，空转不行。

#### 检查是"可执行"的，不是"模型自评"

Weave 的核心契约（`docs/weave.md`）：

> "Executed checks provide the evidence for handoffs and determine whether the final
> delivery passes. Failed checks can trigger a bounded sequence of fresh repair sessions."

而且检查需要**两个条件同时成立**：

> "Weave requires both `ok` and `executed` for a passing check."

`executed` 这个字段是关键：**"检查通过了"必须同时意味着"检查真的跑了"**。
这防的正是我们的老毛病——`real-sheet-baseline-0` 的 harness 说 19/24 PASSED，
代理测试说 1/28。**如果当时有 `executed` 这个约束，那个幻觉在当天就会暴露。**

修复的进展判定也是可执行的（`run_weave` 的 adapter 契约）：

```python
WeaveCheck(
    ok=report["passed"],
    executed=report["executed"],
    repair_targets=tuple(report["failed_targets"]),      # 下一轮修谁
    progress_markers=tuple(report["passed_targets"]),    # 这轮有没有进展
)
```

`progress_markers` 让"有没有进展"变成**可比较的集合**，而不是模型的自我感觉。

#### 那 Team 模式呢？——它恰恰证明了"多 agent 更贵"

Team 是他们真正的研究对象。他们发现一个现象，叫 **illusion of collaboration**：

> "在 OpenCollab 的 trace 里，它们经常没有真的协作：lead agent 向队友交代了任务，
> 然后自己把活干了；或者在交接之前就花光了整个 token 预算。声明出来的团队
> 塌缩成了单个 agent。"

量化指标 **Adherence（遵从度）= 真正按声明组织的运行占比**：

| 对参考团队的改动 | Adherence |
| --- | ---: |
| 无（Qwen3.8-Flash，开放提示，全部工具，星型拓扑） | **47.2%** |
| 提示让交接变成强制 | 91.7% |
| **lead agent 只给只读工具** | **94.4%** |
| 每个角色都用 GPT-5.6-Luna | 97.2% |

**47.2% 的含义**：超过一半的运行里，你付了 briefing 的 token，但协作没发生，
lead 自己又干了一遍。**这就是"多 agent 更贵"的精确形式**——不是 agent 数量贵，
是**协作失败时的重复劳动贵**。

而"只给 lead 只读工具"把遵从度拉到 94.4%，是因为**它让"不协作"变成不可行**。
这条对我们的启示不是"去做多 agent"，而是：**想让某个行为发生，就让它成为
唯一可行路径。**

#### 小结：第一名到底赢在哪

| 层次 | 具体做法 | 为什么省 / 为什么有效 |
| --- | --- | --- |
| **上下文** | 每组 fresh session | `O(N)` vs `O(N²)`；前缀全命中缓存（30× 便宜） |
| **并发** | `concurrency=1` | 避免合并冲突与 workspace 争抢 |
| **检查** | 可执行 + `executed` 双条件 | 杜绝"假通过"（我们的 25 倍幻觉） |
| **修复** | 3 轮 + 2 轮无进展即停 | 有界 |
| **预算** | 分层（总/主/修复）+ 软预算按真实产出扩展 | 钱跟着证据走 |
| **组织** | 不用 Team | 因为 Team 的协作失败率 52.8% |

**它赢的不是"多 agent"，是"把上下文切碎 + 用可执行检查裁决"。**
这两条，VOLO（一次起草）和 arc_pi（契约检查）用完全不同的拓扑实现了同一件事。

#### 我们能直接抄的三件事

| 可抄的 | 我们现在 | 改动量 |
| --- | --- | --- |
| **`executed` 双条件** | `verify_node.py` 只判 exit code | 小：验收器额外输出"实际跑了几个 spec / 几个 error" |
| **`progress_markers`** | 停摆刀用场景签名比对（等价物已有） | 无需改，我们这条已经对 |
| **每组预留检查时间** | `verify_timeout = 1800s` 固定值 | 中：改成按组时间的比例 |

**不能直接抄的**：`concurrency=1` 我们已经是串行了；`fresh session` 我们的
`octos serve --stdio` 已经是每节点新会话——**问题出在节点内部的修复轮**，
那部分没有切分。这才是我们要改的地方。

## 三、代码级对照：七条分岔

这一节是本文的核心。每条分岔都给出**双方的具体实现或常量**，而不是形容词。

### 分岔 1 · 上下文：无界增长 vs 三种切分

> 这一条原来叫"起草：多轮工具循环 vs 一次调用"，容易让人以为是"调用次数"的差别。
> 它其实是**上下文管理**的差别——三支队伍用三种不同手段解决同一个问题。

#### 三种切分手段

| 队伍 | 手段 | 每个"工作单元"的上下文 |
| --- | --- | --- |
| **我们** | 无切分：一个节点内的修复轮持续累积 | `P + kC`，随轮次线性增长 |
| **VOLO** | **一次调用**：全部信息压进一个请求，没有第二轮 | `P + C`，固定 |
| **OpenCollab** | **每单元新会话**：每组/每轮修复重开 | `P + C`，固定且前缀全命中缓存 |
| **arc_pi** | **交接笔记**：上下文用超 80% 时写笔记，新会话从笔记继续 | `P + C`，固定 |

三种手段的数学结果完全一样：把 `O(N²)` 压成 `O(N)`。差别只在工程形态：

- VOLO 的做法要求"一个请求能装下全部信息"——只适合中小应用；
- Weave 的做法可以处理任意大的应用——每组装得下就行；
- arc_pi 的做法是折中——允许一个会话内多次交互，超阈值才切换。

#### 结构对比（我们 vs VOLO）

| | 我们 | VOLO |
| --- | --- | --- |
| 编排单元 | **DAG 节点**：`seed → impl₁ → check₁ → impl₂ → … → check_all` | **一次调用**：需求+卡+源码 → 一个请求 |
| 修复触发 | 验收节点失败 → DAG 回边 → 重跑 impl 节点 | 起草后一次全量检查 → 有界修复序列 |
| 上下文形态 | 每节点独立会话；修复轮重发整个文件 | 一次请求包含全部信息 |
| 单文件规模 | keep 前端后期 50–60K chars | 旧源码有界快照 ≤ 2 MiB / 256 文件 |

#### 我们的成本结构（台账 #0，keep 32 节点）

```
phase      请求数    prompt tokens         completion     模型时间
repair     127 (79%)  4.96M (92%)          190K           28.5 min
implement   34        0.45M                363K (65%)     31.0 min
```

**79% 的请求在修复，92% 的 prompt token 在修复。**

T2 stackoverflow 更极端（台账 #2）：

| 指标 | 读数 |
| --- | --- |
| 总请求 | 1331 |
| repair 占比 | **100%** |
| prompt tokens | 65.4M（93% 缓存） |
| 中位数上下文 | 106K chars |
| >100K chars 的请求 | 1107 / 1331 |
| 花费 | $9.30 |

#### 对比读数

| 方案 | 结果 | 花费 |
| --- | ---: | ---: |
| VOLO 多轮工具循环（Keep） | 22/32 | ¥12.03 |
| **VOLO 一次调用（Keep）** | **27/32、29/32** | **¥0.88–0.94** |

**质量更高，成本低 13 倍。**

#### 为什么一次更好（机制解释）

多轮修复的每一轮都在**重发整个上下文**。我们实测：

- keep 修复轮基底 ≈ 90K chars；
- top3 修复循环各 20/20/17 迭代，messages 累到 64–164 条；
- 单个循环 prompt 72–108 万 tokens；
- **前 3 个循环占全部 repair 请求的 45%**。

模型在 100K+ chars 的会话里做小步挪动，收敛慢且容易改坏别处。VOLO 的
`REPAIR_SHOWN = 40`（一次修复只列 40 个失败场景）也是同一个思路：**给模型看
它能消化的量**。

> **但这条也有代价。** VOLO 自己承认了（`2026-10-02-generalization-bottlenecks.md`）：
> "测试与实现会共享需求误读……某些检查只确认可见提示，某些前置条件被跳过。"
> 他们的缓解手段是"让同一个模型看不到应用"——减少共享上下文，但共享的**需求理解**
> 无法消除。这是这个方案的固有风险，不是我们的错觉。

### 分岔 3 · 修复：无界整文件重发 vs 有界定点编辑

#### 参数对照表

#### 我们的"5 轮"其实是"5 次整文件重发"

`arc-policy.toml`：

```toml
[repair]
rounds = 5              # OCTOS_REPAIR_ROUNDS — K, acceptance repair rounds per node
rounds_large_tree = 3   # trees with more than large_tree_nodes ATOMIC nodes
stall_limit = 2         # stop a node after this many repairs without improvement
```

听起来有界。但每一轮是**整文件重发**：keep 的单文件前端到后期 50–60K chars，
每轮重发整个文件；stackoverflow 中位数上下文 106K。

VOLO 的读数：**整份重发大文件每轮弄坏约 10 条**；定点编辑让同一份初稿从 25 到 38。

#### VOLO 的 `_apply_hunk`：一个值得抄的实现

他们的 SEARCH/REPLACE 不是朴素字符串替换，而是带**容错与可解释失败**：

```python
def _apply_hunk(content, search, replace, where):
    """Replace the one place `search` occurs: verbatim first, then line by line
    ignoring each line's surrounding whitespace (a model re-indents what it copies).
    Zero or several places raise HunkMiss naming the hunk and quoting the current
    lines nearest to it."""
    count = content.count(search)
    if count == 1:
        return content.replace(search, replace, 1)
    lines = content.splitlines(keepends=True)
    want = [line.strip() for line in search.strip("\n").splitlines()]
    hits = [i for i in range(len(lines) - len(want) + 1)
            if all(lines[i + k].strip() == want[k] for k in range(len(want)))]
    if len(hits) != 1:
        near = _nearest(lines, want)
        raise HunkMiss(f"{where}: SEARCH matches nothing (it starts `{first}`)"
                       + (f"; the current lines there are:\n{near}" if near else ""))
```

三个设计：

1. **先精确、再忽略缩进**——模型会重新缩进它复制的代码；
2. **匹配多处也报错**，不猜"第一个"；
3. **失败时把当前位置的真实代码贴给模型**（`_nearest` 用 `difflib.SequenceMatcher`
   找最像的 14 行）——**错误信息本身就是修复指令**。

对照我们：整文件重写没有"匹配失败"这个概念，所以也就没有可解释的失败。

### 分岔 5 · 实验纪律：台账 vs 判据

| | 我们 | VOLO |
| --- | --- | --- |
| 记录量 | 39 行台账 | **116 条实验** |
| 事前判据 | ❌ 多数没有 | ✅ 每行都有"判据（事先写死的）" |
| 按判据砍掉 | 少数 | **42 条** |
| 单样本 vs 配对 | 多为单样本 | 09-23 起强制配对六题样本 |
| 分辨力估计 | 无 | **单样本只能分辨 24–32 个百分点** |

VOLO 在 09-23 做的决定，我认为是他们整届最重要的一个：

> "23 个独立样本没有一个满分，相邻两版差 5 到 8 分，落在噪声里。我们停掉单样本
> 迭代，改成每个机制先写死判据再上场。"

**我们的台账里，多数结论建立在单样本上。** 比如"某刀有效，62 → 77"——
按他们的分辨力估计，这个差异可能有一半是噪声。

### 分岔 6 · 交付：回退链 vs 永不交付空

| | 我们 | VOLO |
| --- | --- | --- |
| 机制 | `.arc-good`（最后过检）+ `.arc-best`（全量回归）+ 每 60s 渐进交付 | `delivery_complete()` 检查 + `generate()` 的兜底分支 |
| 原则 | 交付"最后过检态" | **永不交付空** |

VOLO 的 `generate()` 兜底（源码）：

```python
except Exception as exc:
    # Preserve the last complete application after a spent budget, a transport
    # failure, a protocol error or a crash in the checks: the stage holds every
    # complete file written so far (never a partial one), and it ships when it
    # passes the delivery check.
    if not delivery_complete(stage):
        raise
    reason = str(exc).replace(key, "[REDACTED]") if key else str(exc)
    print(f"[oneshot] delivering the last complete version after an error: {reason}", file=sys.stderr)
```

注意 `if not delivery_complete(stage): raise`——**如果连完整版本都没有，宁可报错
也不交付半成品**。这是"永不交付空"的精确含义：**要么交付完整，要么明确失败**。

我们的历史事故（台账 #23，arch-6）：

- `collect_app` 只认 `.arc-best`（全量回归快照，仅管线走完全程才存在）；
- 墙掐跑走不到全量回归 → 回退到裸最终工作区 = 半成品 + 脏 store；
- 结果 **7/100**。

我们后来修了（回退链补 `.arc-good`），但这是**补漏**，不是原则。

### 分岔 7 · 成本观：事后刹车 vs 架构选择

| | 我们 | VOLO |
| --- | --- | --- |
| 单跑最高 | **¥104.8**（github-arch-0，8h，220M token） | 决赛两题 **¥2.56** |
| sheet 单题 | ¥49（41 分） | 初赛两题 ¥6.35（166 分） |
| 成本控制机制 | 停摆刀 + 燃料表（**10-01 落地**） | 一次起草（09-15）+ 有界修复（09-23）+ 缓存前缀（09-27） |
| 成本控制性质 | **事后刹车** | **架构选择** |

#### 边际汇率：一个我们算晚了的数

计分公式 `S = p·(B/b)^0.2`，两个偏导：

```
∂S/∂p = S/p
∂S/∂b = -0.2·S/b
```

在 p = 25、b = ¥49 时：

| 量 | 值 |
| --- | --- |
| 一个通过率点的价值 | `S/25` |
| 一元钱的价值 | `0.2·S/49` |
| **一个点 ≈ 多少元** | **49 / (0.2 × 25) = ¥9.8** |

**一个通过率点 ≈ ¥10。** 所以：

- 任何花不到 ¥10 能换一个点的改动，**都值得做**；
- 任何省不到 ¥10 却损失一个点的改动，**都不值得**。

我们直到 10-02 才写下这句话。而停摆刀和燃料表是在 10-01 落地的——**它们在
p 只有 25-41 的时候优化了错误的对象**。

VOLO 没有这个问题，因为他们的成本控制是架构选择：一次起草天然便宜（¥0.9/题），
不需要事后刹车。

## 五、他们对在哪：六条可迁移原则

### 1. 一次做对 > 反复修对

**读数**：VOLO 多轮 22/32 ¥12 vs 一次 29/32 ¥0.9。**质量更高，成本低 13 倍。**

**机制**：多轮修复每轮重发整个上下文（我们实测 90-106K chars/请求）。一次起草把
所有信息压进一个请求，模型看到的是完整任务。

**可迁移**：任何"生成 + 验证 + 修复"循环，先问"能不能一次生成对"。

### 2. 能做成门禁的，不要写进提示词

**读数**：VOLO 消融——删掉卡片里题目形状规则，六题均值 65.2/58.7 → 55.3/45.7。

**分级**：

```
门禁（代码检查 + 有界修复） > 脚手架原语 > 从需求算出来的表 > 散文规则
```

**可迁移**：每次想往提示词里加一条规则，先问"能不能写成检查"。

### 3. 测试是反馈工具，不是评分工具

**读数**：VOLO 自写测试接进修复环后 Sheet 43 → 53 → 79。

**关键设计**：让**同一个模型**只读需求写测试——测试天然可进包、不泄漏隐藏信息。

**风险**（VOLO 自己承认）：测试与实现共享需求误读，无法完全消除。

**可迁移**：如果测试不能驱动修复，它就只是评分。

### 4. 判据先写，再跑

**读数**：VOLO 23 个样本 0 满分，相邻版本差 5-8 分 = 噪声。

**规则**：每个机制上场前写下：假设、判据、读数、去留。读数不达判据就撤，不解释。

**可迁移**：单样本对单样本只能分辨 24-32 个百分点（VOLO 估计）。预期提升小于
这个数，就需要配对样本，或者不要做。

### 5. 让行为成为唯一可行路径，而不是请求它

**读数**：OpenCollab 的 Team 控制器——只把 lead agent 工具改成只读，Adherence
从 47.2% 到 94.4%。

**机制**：lead 没法自己干活，只能真的委派。

**注意**：这条是**研究结论**，不是他们的比赛配置——比赛用的是 Weave（单 agent
+ 新会话），见 [2.3 节](#23-opencollab--第一名靠的是上下文切分不是多-agent)。
这条对我们的价值是它的一般形式：**想让某个行为发生，就让它成为唯一可行路径。**

**可迁移**：任何"希望模型这样做"的需求，先问"能不能让它不做就失败"。
**提示词是请求，门禁是强制。**

### 6. 永不交付空

**读数**：VOLO 截断与断流曾让整题零分 → 改成"任何异常后交付最后一个完整版本"。

**精确含义**（源码）：`if not delivery_complete(stage): raise`——**要么完整，要么明确失败**。

**可迁移**：交付路径上每一条异常分支都要有"至少交付什么"的答案。

## 六、为什么我们没有走到那条路

这一节写给下一届的自己。不是找借口，是找**可修正的决策模式**。

### 1. 我们被"官方模板"锚定了

我们用 `octos-arc`——官方团队的参赛版。它有完整骨架：DAG、节点、验收、修复回边。
这套架构是"官方推荐"，所以我们默认它是对的。

但官方模板本身也是**一个参赛方案**，不是最优解。VOLO 和 arc_pi 都是自建 harness，
从零选择架构。

**教训**：拿成熟框架当起点是优势（省时间），但要定期问"这个框架的核心假设还
成立吗"。我们的核心假设是"逐节点修复能收敛"，它在弱模型上不成立。

### 2. 我们把"机制数量"当成了进展

39 行台账里，机制一条一条加：D3、C1a、R1、R2、R3、R4、E1、E3、A19、A20……
每条都有尸检、有读数、有代码。看起来非常扎实。

但这些机制大多是**在错误的主路径上打补丁**。主路径是"多轮修复"，所有机制都在
让它更高效一点。VOLO 做的是**换主路径**。

**教训**：机制数量是虚荣指标。真正的问题是"主路径对不对"。

### 3. 我们过早优化了成本

¥65/12h 的尸检让我们非常难受，于是做了停摆刀和燃料表。这两个机制本身很好
（VOLO 也有"2 轮无进展即停"）。

但我们在 p 只有 25-41 时把注意力放在了 b 上。一个点 ≈ ¥10——这个数我们算得太晚。

**教训**：先算边际汇率，再决定优化什么。

### 4. 我们没有把"本地全绿"当成需要验证的假设

`real-sheet-baseline-0` 的 19/24 vs 1/28 是 09-24 就发现的。我们记录了它，
但没有因此改变方法。

**教训**：当一个测量结果和另一个差 25 倍时，**先修测量，再修被测对象**。
我们反过来了。

### 5. 我们太晚才读对手

比赛期间我们读官方文档、需求、平台规则。赛后读三个头部仓库，发现他们的关键
决策（一次起草、自写测试、3:1 规则）都在 09-15 到 09-25 之间就做了。

**教训**：开源比赛的对手仓库是公开情报。开赛第一周就该读。

### 6. 我们的配置与代码在合并中脱节（见第七章）

这是最不该发生的一类错误：**我们以为在调 A，实际在调 B**。

### 7.4 根因与修法

**根因**：09-26 的上游合并是一次**架构替换**（旧 orchestrator → 新 pipeline 引擎），
但 `arc-policy.toml` 作为"唯一旋钮表"被完整保留。没有测试检查"配置键是否被消费"。

**修法**（三选一，按成本排序）：

1. **最小**：加一个测试，遍历 `arc-policy.toml` 的键，断言每个都在代码里有引用
   （或显式标记 `# dead: <理由>`）。成本：约 50 行。
2. **中等**：删除死配置，把 `arc-policy.toml` 收敛到实际被读的 32 个键。
3. **彻底**：让 `policy()` 反向工作——从代码声明生成 `arc-policy.toml`，而不是
   从 toml 读取。这样"配置即文档"不会漂移。

**这条教训的普适性**：任何"配置表 + 代码消费者"的架构，都需要一个
**接线测试**。否则配置会变成一种**安慰剂**——你以为在调，其实没接。

### 7.5 它对我们复盘的影响

这一发现让两条台账结论打了折扣：

| 台账 | 原结论 | 实际有效期 |
| --- | --- | --- |
| #7 C1a | token −35% | 仅对 09-23 ~ 09-26 的旧架构成立 |
| #9 E1 | implement_fraction 0.6→0.8 | 09-26 合并后失效 |

**但整体结论不变**：这些是单条机制的局部失效，不影响"多轮修复是主路径、
成本超线性"这个主判断——那个判断建立在 #0/#2 的**请求结构统计**上，
不依赖任何配置键。

## 八、如果重来一次：可执行清单与工作量估算

按投入产出排序。前三条我认为能单独把分数抬到 70+。

### 第 1 周就要做的（架构级）

#### ① 把起草改成一次调用

**做什么**：需求节点 + 已实现源码 + 种子清单 + 方言卡，压进**一个请求**，温度 0；
只输出改动或新增的完整文件；截断就续写。

**工作量**：3–5 人日（要重写 `main.py` 的 DAG 生成部分，保留 verify 链路）。

**预期**：单节点成本降一个数量级，首过率上升。

**风险**：现有 DAG 的"回边修复"能力会失去——需要用 VOLO 式的有界修复序列替代。

#### ② 源码级契约检查，不调模型

**做什么**：把 `aria_lint.py` 从"生成 Playwright spec 跑 DOM"改成"扫源码文本"：

- 需求里每个 `引号名字` 必须作为字符串出现在 `frontend/src/**`；
- 每个 GIVEN 反引号值必须出现在 `backend/seed-default.json`（或 seed 函数）；
- 每个 THEN 引号消息必须出现在源码里。

**关键细节**（直接可抄 arc_pi 的三个判断）：
- 区分 UI 名与示例输入（排除邮箱/密码/slug/范围）；
- 区分种子与待创建（"does not yet exist" 的句子整体跳过）；
- 缺漏列表上限 30 条。

**工作量**：0.5–1 人日。

**预期**：零 LLM 成本、零浏览器、毫秒级反馈，覆盖大部分"名字写错"类失败。

#### ③ 自写测试接进修复环

**做什么**：

- 平台跑里，`main.py` 用**同一个模型**只读需求生成 spec（不看应用）；
- spec 进 `verify_node.py` 的验收命令；
- 修复轮以 spec 失败为信号；
- spec 自身报错记为 error，不驱动修复；
- 绕过 UI 的 spec（直接 URL、调 API、CSS 选择器）删掉。

**工作量**：2–3 人日。

**预期**：VOLO 的读数是 Sheet 43 → 53 → 79。

**风险**：测试与实现共享需求误读（VOLO 已承认）。缓解：测试写完后用"看不到应用"
的独立会话复核。

### 第 2 周做的（机制级）

#### ④ 有界修复 + 3:1 接受规则

**做什么**：

- 只许定点编辑（SEARCH/REPLACE），禁止整文件重发；
- 每次修复后重跑全量 spec，**每丢 1 条至少多过 3 条**才接受，否则回滚；
- 五个独立上限：调用数 24 / 花费 ¥10 / 连续被拒 4 / 时间 3h / 失败列表 40 条。

**工作量**：2 人日（`_apply_hunk` 的容错逻辑值得直接移植）。

#### ⑤ 确定性旧行为守卫

**做什么**：

- 起草前在隔离副本上遍历起点应用两遍、取交集作基线；
- 每个版本按原路径重放，基线项丢了就**否决**该改动（否决权，不是权重）；
- 需求写明的改名/删除豁免。

**工作量**：3 人日（VOLO 的 `regression_guard.py` + `regression_probe.cjs` 可参考）。

#### ⑥ 知识下沉

**做什么**：把 13KB 提示词逐条分类——能写成门禁的写成门禁，能进脚手架的进脚手架，
剩下才是方言卡。目标：卡片 ≤ 60 行。

**工作量**：1 人日（分类）+ 逐条实施（视条目数）。

### 贯穿全程的（纪律级）

#### ⑦ 判据前置

每个机制上场前写下：假设、判据、读数、去留。读数不达判据就撤，不解释。
**已经能拿高分的版本也要按判据删。**

#### ⑧ 一次只改一处

每次提交只允许一个机制 diff；多机制改动必须拆成多个候选，分别读数。

#### ⑨ 方向切换截止时间

```
切换截止 = 比赛截止 − 2 × 一次完整平台往返（4-12h） − 1 次回滚余量
```

过了这个点只做参数调整，不做架构变更。

#### ⑩ 开赛第一周读对手仓库

三个头部仓库的关键决策都在 09-15 到 09-25 之间做了。这些是公开情报。

#### ⑪ 配置接线测试（本次新增）

任何"配置表 + 代码消费者"架构，必须有测试断言**每个配置键都被消费**。
见[第七章](#七代码审计发现我们自己的一处系统性缺陷)。

## 十、诚实的局限与对照的有效性

### 10.1 我们的结论有哪些不确定性

1. **很多结论只有一两个读数。** 单跑方差很大（同一个包 sheet 在 62 附近抖动，
   github 在 0-5 之间跳）。VOLO 估计单样本只能分辨 24-32 个百分点。
2. **本地分来自代理裁判。** 我们自己的分析显示代理套件偏乐观（同一产物本地 97、
   平台 41）。任何"本地满分"都要打折。
3. **平台分受外部变化影响。** 09-24 发错题、09-25 套件修复、需求两次改版，都混进
   了成绩曲线。VOLO 也遇到同样的事（10-02 主办方更新 GitHub 需求，同一提交
   GitHub 从 18 到 46），他们明确写了"这一跳不能算我们的功劳"。
4. **改动常打包上场。** 见错误 5。
5. **我们从未拿到平台的逐测试明细。** 只有总通过率，归因只能靠本地复现。
6. **"42/16" 是最终入账，不是能力上限。** 本地隔离尺 62/51 说明产物本身比平台分好。
7. **配置漂移**（第七章）：两条台账结论已失效。

### 10.2 对照本身的有效性

这一节是自我审查：**我用什么标准判断"他们更好"？**

| 判断 | 依据 | 强度 |
| --- | --- | --- |
| 一次起草优于多轮修复 | VOLO 的同题对照（22/32 ¥12 vs 29/32 ¥0.9） | **强**（同模型、同题、有成本读数） |
| 源码级契约检查有效 | arc_pi 的源码 + 文档描述 | **中**（无 A/B 读数，只有机制存在） |
| 3:1 规则优于只增不减 | VOLO 的 31 次修复零下降 | **中**（无对照臂，只有"没有变差"） |
| 守卫有效 | 8/8 合成破坏 + 134/132 真回归分类 | **强**（有阳性/阴性对照） |
| Adherence 机制有效 | 47.2% → 94.4%（只改工具权限） | **强**（单变量对照） |
| 新会话更省 token | `O(N²)` vs `O(N)` 推导 + 缓存 30× 价差 + 我们的 106K 中位数实证 | **强**（数学 + 我方实证；但缺对方同题 A/B） |
| 判据前置优于无判据 | VOLO 的 42 条砍掉记录 | **中**（无法证明"如果不砍会更好"） |

**最弱的一环**：我们把"他们的机制"当成"有效的机制"，但他们的**分数**是多个机制
叠加的结果，无法归因到单条。比如 VOLO 的 166/200 里，一次起草贡献多少、
自写测试贡献多少、守卫贡献多少——**他们没有做完整的消融**。

**所以本文的定位是**：不是"照抄这些机制就能拿高分"，而是"这些机制解决的是
真实存在的问题，而这些问题我们也有"。

### 10.3 关于三支队伍的信息边界

- 我们读到的是他们**公开的文档与源码**，不是内部过程。
- 他们也可能有大量未公开的失败与回撤。VOLO 的 116 条实验和 42 条砍掉是公开的，
  这值得敬佩；我们只能看到这一面。
- OpenCollab 的论文级统计（arXiv 2609.38345）比另外两家更系统。但要注意
  **论文研究的是 Team 控制器，比赛提交用的是 Weave**——两者不能混为一谈。
  另外 `examples/arcbench-evolution-r6/` 是决赛版，我们没有他们的初赛数据。
- arc_pi 的引擎（Pi agent）是预构建 bundle，源码不在仓库里——**我们无法评估
  引擎本身的贡献**。

## 十一、一句话

> 我们造了一台能自我诊断的机器，却没来得及让它一次就把事情做对。

机制、尸检、实验纪律都立住了；输在**实现路径的选择**——用多轮修复去弥补
一次实现的不完整，而这条路在弱模型上成本超线性、收敛不可靠。

三支头部队伍用同一个模型，证明了差距不在模型，在 harness。他们的共同选择是：

| 原则 | 证据 |
| --- | --- |
| **一次做对** | VOLO 一次起草 29/32 ¥0.9（多轮 22/32 ¥12） |
| **确定性检查** | arc_pi 契约检查零 LLM；VOLO 守卫 8/8 检出 |
| **测试驱动修复** | VOLO 自写测试接环，Sheet 43 → 79 |
| **判据前置** | VOLO 116 条实验砍掉 42 条（含 S 110 的版本） |
| **切碎上下文** | OpenCollab 每单元新会话（`O(N²)`→`O(N)`）；VOLO 一次调用；arc_pi 交接笔记 |
| **让行为成为唯一路径** | OpenCollab Team：只读工具让 Adherence 47.2% → 94.4% |
| **永不交付空** | VOLO `if not delivery_complete(stage): raise` |

下次把顺序倒过来：**先保证一次做对，再谈怎么修。**
