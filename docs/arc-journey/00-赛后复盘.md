## 二、我们做对了什么（有证据的）

这几条我认为放到任何一届都成立，值得保留。

### 1. 先有尸检，再有刀

39 行实验台账里，几乎没有一条机制是"觉得应该有用"加上去的。每条都对应一次
具体的失败：

| 刀 | 尸检来源 | 效果 |
| --- | --- | --- |
| 语法刀 | `app.js:1242` 缺右括号 → 11 个场景全灭，Playwright 只报"列表空" | 把 `file:line` 直接喂给修复轮 |
| 资产洞探针 | 路由白名单漏 `/app.js` → 全站 JS 死 → 平台 0/100 | 检查先探根绝对路径 .js/.css 404 |
| 种子金丝雀 | 中段节点重写全局 `seed()` → 毒化 `.arc-good` → 6/100 | 每节点强制首需求 spec 为金丝雀 |
| 停摆刀 | ¥65/12h 尸检：钱 ≈ impl 重执行次数 × 单价，浪费在无望节点 | 连续 2 轮签名不动即弃修 |
| 燃料表 | T1 尸检：平台计费 ≈ 内核 meter 的 827 倍，$5.5 阈值永不触发 | 双轴（meter + token）止损 |

这个习惯让我们在**没有官方测试**的情况下，仍然能把分数从 25 稳定推到 41-42。

### 2. 环内验证是胜负手

旧路线（Aurora-X 自研编排）在 keep REQ-2 子树 23 节点上 15/23，8 个失败全是
后期节点回归——因为没有环内测试。octos-arc 的「逐节点本地跑验收 spec + 修复
≤5 轮 + 回归检查点」把 keep 做到了 32/32。

这条判断后来被头部队伍独立验证：volo 的第二步就是"让同一个模型只看需求、
不看应用，写浏览器验收测试，再用这些测试驱动修复"。

### 3. 代理测试 + 需求契约提取

官方真实测试从未流出。我们做了两件事：

- `aria_lint.py`：从需求文档提取「role + 反引号名字」契约，每验收轮生成 lint spec。
  在 bookstack 上真捕获 3 处（REQ-4.1 / 4.2.1 / 6.3.1），零误报。
- `arc/proxy-tests/`：依需求逐字写的保密代理套件（sheet 28 例、github 44 spec、
  Zcode 200 用例），对 octos 全程不可见。

方向是对的。**但见下一节：我们没把它接进平台的修复环。**

### 4. 把"平台语义"当成一等公民去研究

我们花了很多时间搞清楚：共享会话污染、世界不重播种、`>20` 整套豁免触发渗血、
24h 软杀无评估、计费口径 827 倍。这些在别的队伍那里大多是黑箱。

[`14-世界对账与平台语义.md`](14-世界对账与平台语义.md) 里那张四配置对照表（102 / 84 / 77 /
33 vs 官方 41）是这次最有价值的单篇分析：它证明了**同一产物本地 97、平台 41
的主体是评分语义差异，不是应用质量**。

## 三、我们错在哪（按影响排序）

### 错误 1：把"多轮工具修复"当成主路径（最大）

台账 #0 的成本结构：

```
repair    127 请求（79%）  prompt 4.96M（92%）  completion 190K
implement  34 请求         prompt 0.45M          completion 363K（65%）
```

T2 stackoverflow 更极端：**1331 个请求 100% 全是 repair**，prompt 65.4M，
中位数上下文 106K。修复循环成了成本黑洞，而它修的是**上一轮实现没做对的东西**。

头部队伍在这件事上的结论完全相反：

- volo（09-15）：同一道 keep，多轮循环 186 次调用 22/32、¥12.03；
  **一次调用 + 一张方言卡，27/32 和 29/32，每次不到 ¥1**。当天就把多轮内核停掉了。
- volo 的修复环是**有界的**：只许定点编辑（SEARCH/REPLACE），每丢 1 条至少多过
  3 条才保留，24 次调用 / ¥10 / 连续 4 次丢弃即停。
- arc_pi：每批需求一次起草，**每次改动后立刻 build**，build 失败才进修复。

我们的修复环是"失败 → 整个文件重发 → 再失败 → 再重发"。keep 的 codegen 每节点
整文件重写，单文件架构放大了这个成本。这不是提示词问题，是**架构问题**。

### 错误 2：验收信号停留在"存在性"，没到"行为"

`aria_lint` 检查的是 DOM 里有没有 `role=grid` 且 `aria-label="Worksheet grid"`。
它测不出：

- 点了 Import CSV 之后对话框里有没有正确的字段
- 排序之后行序对不对
- 公式算出来的值对不对

所以 `real-sheet-baseline-0` 出现了一个残酷的对照：**harness 判 19/24 ATOMIC
PASSED，代理测试判 1/28（4%）**。25 倍的差距，全是幻觉。

我们后来用 proxy-tests 补上了这一层，但那是**本地保密套件**，不进平台包、
不进 agent 工作区——它对平台跑没有直接作用。而头部队伍的做法是：

- volo：同一个模型**看不到应用**，只读需求写 Playwright 测试，然后把测试
  **接进修复环**（Sheet 43 → 79）。
- arc_pi：**契约检查不调模型**——需求里每个引号名字必须出现在源码里，每个
  反引号 GIVEN 值必须由后端创建。这是源码级检查，比 DOM 级检查便宜且更早。

我们想到了（`aria_lint` 就是从需求提取契约），但只做了一半：提取了、没进环。

### 错误 3：冷启动天花板被误读成"墙不够长"

我们在 09-30 把冷启天花板钉死在 25-26，结论是"墙是冷启抬升的唯一杠杆"，
于是把 6h 墙一路加到 24h。

事后看这是**症状不是病因**。真正的病因是：deepseek-v4-flash 在 6h 内建不完
24 个节点，因为每个节点都要走"实现 → 验收 → 修复 → 再验收"的长链。
头部队伍在同一模型上的做法是**一次起草 + 确定性门禁 + 有界修复**，
单节点轮次少一个数量级。

加墙能买到更多节点，但买不到"一次做对"。所以我们最后看到的现象是：
节点数够了（24/24 全触达）、分数还是 41。

### 错误 4：最后 48 小时的方向切换没有落地时间

10-02 我们才开始做 stage 拆分（把 47 节点的 github 拆成 12+14+21）、
视觉语义入链、外聘 Agent 建产物。这些方向本身是对的——stage-1 本地确实做到了
30/30、stage-2 29/29——但：

- 平台最后一票跑的是 stage 树，stage-2/3 **一分未得**；
- 本地全绿 ≠ 平台全绿，我们又一次没有留出"本地绿 → 平台验证"的往返时间。

教训很直白：**方向切换的截止时间不是比赛截止时间，是"截止时间 − 一次完整
平台往返（4-12h）− 一次回滚余量"。**

### 错误 5：多变量同时上车，归因失效

台账里多次出现"联合腿"：D3.2 + E1 + E3 一起上、架构合并 + 多把刀一起上。
当结果是 1/28 时，我们无法判断是哪一项造成的。

我们自己在 `04` 里写了"一次只改一处"，但在时间压力下反复违反。头部队伍把
这条做成了硬规则：volo 的 116 条实验里，只有标为消融的几组是一次只改一处，
其余都在文档里明确标注"改动常打包上场"——**他们承认局限，我们假装没有**。

### 错误 6：成本控制来得太晚

¥65/12h 的尸检发生在 10-01，比赛 10-03 结束。停摆刀和燃料表落地时，
只剩两票的机会。而计分公式 `S = p·(B/b)^0.2` 里 b 是**弱惩罚**（b 翻倍 S×0.87），
p 是**线性主导**（p 翻倍 S×2）——我们花了大量时间优化 b，而 p 才是主战场。

这不是说成本不重要，而是：**在 p 很低的时候，任何成本优化都是次要的**。
我们直到 10-02 才明确写下这句话。

## 四、头部队伍怎么做的

赛后读了三个公开仓库。它们的机制复杂度**不比我们高**，差别在几个关键选择上。

| 维度 | 我们（octos-arc） | volo-factory（决赛第 2） | arc_pi（Limitless） | OpenCollab（第 1） |
| --- | --- | --- | --- | --- |
| 起草 | 多轮工具循环，逐节点 | **一次调用起草**（温度 0） | 每批需求一次起草 | Duo：双 coder + analyst 委派 |
| 验收 | DOM 存在性 lint | 自写测试 + **源码级契约检查** | 自写测试 + **契约检查（不调模型）** | 可执行检查（executable checks） |
| 修复 | 无界，整文件重发 | 定点编辑 + **3:1 接受规则** | 定点编辑 + 3 轮上限 | **有界修复 + 继续**（bounded repair and continuation） |
| 交付 | `.arc-good` 回退 | **永不交付空** | best snapshot | 有序会话 |
| 知识形态 | 提示词 + lint | **能做成门禁就不写进提示词** | 方言卡（默认做法） | team/workflow 声明 |
| 实验纪律 | 台账，但常多变量 | **判据写死，116 条实验砍掉 42 条** | 配置表 | 论文级统计 |

三个共同点，也是我们最该学的：

### 1. 一次做对 > 反复修对

volo 的数字最刺眼：多轮 22/32 ¥12 vs 一次 29/32 ¥0.9。**质量更高，成本低 13 倍。**

原因不难理解：多轮修复的每一轮都在**重发整个上下文**（我们实测 90-106K
chars/请求），模型在巨大的上下文里做小步挪动，收敛慢且容易改坏别处。
一次起草把所有信息压进一个请求，模型看到的是完整任务。

### 2. 能做成门禁的，不要写进提示词

volo 的 ADR 0001 把这条列为第一原则，分三级：门禁 > 脚手架 > 方言卡（提示词）。

我们的 `aria_lint` 是门禁，方向对；但大量规则仍然写在
`prompts/pipeline-implement.md`（13KB）里，靠模型"记住"。弱模型记不住。

arc_pi 的契约检查是最好的例子：**不调模型**，纯文本匹配——需求里每个引号名字
必须出现在源码里，每个反引号 GIVEN 值必须由后端创建。便宜、确定、早失败。

### 3. 判据先写，再跑

volo 在 09-23 停掉单样本迭代，改成"每个机制先写死判据再上场"。他们的 116 条
实验里，42 条是按读数砍掉的——包括一些"看起来能涨"的改动。

我们的台账有"下一步"，但没有**事前写死的判据**。结果是每次改动后都能找到
理由说"这次不算数，下次会好"。

## 五、如果重来一次（可执行清单）

按投入产出排序。前三条我认为能单独把分数抬到 70+。

### 1. 把起草改成一次调用（1-2 天）

- 需求节点 + 已实现源码 + 种子清单 + 方言卡，压进**一个请求**，温度 0。
- 只输出改动或新增的完整文件；截断就续写。
- 用 `OCTOS_ARC_INLINE_SOURCE_CHARS` 控制内联量（我们已验证 15000 比 40000 省 35%
  token，方向是对的，但还在多轮框架里）。
- 预期：单节点成本降一个数量级，首过率上升。

### 2. 源码级契约检查，不调模型（半天）

把 `aria_lint.py` 从"生成 Playwright spec 跑 DOM"改成"扫源码文本"：

- 需求里每个 `引号名字` 必须作为字符串出现在 `frontend/src/**` 里；
- 每个 GIVEN 反引号值必须出现在 `backend/seed-default.json`（或 seed 函数）里；
- 每个 THEN 引号消息必须出现在源码里。

失败直接喂修复轮。这是**零 LLM 成本、零浏览器、毫秒级**的反馈，
覆盖了 aria_lint 覆盖不到的大部分"名字写错"类失败。

### 3. 自写测试接进修复环（1-2 天）

我们已经有 `arc/proxy-tests/`（github 44 spec + sheet 24 spec）。问题只是它
不进平台包。改成：

- 平台跑里，`main.py` 用**同一个模型**只读需求生成 spec（不看应用）；
- spec 进 `verify_node.py` 的验收命令；
- 修复轮以 spec 失败为信号。

风险：自写测试可能错。缓解：需求文档是唯一真相，spec 里的断言必须能引用
需求原句；spec 自身报错（编译/选择器）记为 error，不驱动修复。

### 4. 有界修复 + 3:1 接受规则（半天）

- 只许定点编辑（SEARCH/REPLACE），禁止整文件重发；
- 每次修复后重跑全量 spec，**每丢 1 条至少多过 3 条**才接受，否则回滚；
- 连续 N 次被拒 / 预算耗尽即停，交付最后一个完整版本。

### 5. 判据前置（贯穿）

每个机制上场前写下：假设、判据、读数、去留。读数不达判据就撤，不解释。

### 6. 方向切换的截止时间（贯穿）

`切换截止 = 比赛截止 − 2 × 一次平台往返`。过了这个点只做参数调整，不做架构变更。

## 七、诚实的局限

写在这里，是因为下一届还会有人踩同样的坑。

1. **很多结论只有一两个读数。** 单跑方差很大（同一个包 sheet 在 62 附近抖动，
   github 在 0-5 之间跳）。我们的"某刀有效"多数是单样本对单样本。
2. **本地分来自代理裁判，不是官方。** 我们自己的分析显示代理套件偏乐观
   （同一产物本地 97、平台 41）。任何"本地满分"的结论都要打折。
3. **平台分也受外部变化影响。** 09-24 发错题、09-25 套件修复、需求两次改版，
   都混进了成绩曲线。
4. **改动常打包上场。** 见错误 5。
5. **我们从未拿到平台的逐测试明细。** 只有总通过率，归因只能靠本地复现。
   这是这次最大的信息劣势，也是头部队伍用"自写测试"绕开的点。
6. **"42/16" 是最终入账，不是我们的能力上限。** 本地隔离尺 62/51 说明产物本身
   比平台分好；但比赛只看平台分。

---

## 八、一句话

> 我们造了一台能自我诊断的机器，却没来得及让它一次就把事情做对。

机制、尸检、实验纪律都立住了；输在**实现路径的选择**——用多轮修复去弥补
一次实现的不完整，而这条路在弱模型上成本超线性、收敛不可靠。

下次把顺序倒过来：**先保证一次做对，再谈怎么修。**
