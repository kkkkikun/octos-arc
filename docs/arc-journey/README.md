## 先说结果

| | sheet（在线表格） | github（协作平台） | 合计 |
| --- | ---: | ---: | ---: |
| **平台最终入账** | **42 / 100** | **16 / 100** | **58 / 200** |
| 历史最高（中途） | 41 / 100 | 4 / 100 | — |
| 本地代理自检（同产物） | 97–102 / 103 | 51 / 100 | — |
| 结论 | 未进前 20，未获奖 | | |

最终得分比中途历史最高（41 + 4 = 45）高出 13 分，两个任务都在最后一票上抬了分：
sheet 41 → 42，github 4 → 16（github 一票翻了 4 倍）。但离入围线仍然很远。

**最诚实的结论**：我们的机制是有效的（github 从 4 抬到 16、sheet 稳定在 41-42、
本地自检 97/103），但**实现速度**和**单次实现的完整度**不够。赛后看头部队伍
（[OpenCollab](https://github.com/RISE-X-Lab/OpenCollab)、
[volo-factory](https://github.com/thunderstone-group/volo-factory-finals)、
[arc_pi](https://github.com/Simonghj/arc_pi_r6)），差距不在"机制复杂度"，
而在**一次实现就做对**的能力——详见 [`00-赛后复盘.md`](00-赛后复盘.md)。

## 我们建了什么

不是"调提示词"，是**一整套让弱模型能持续产出正确 Web 应用的机制栈**。

### 提交物长什么样

```
octos-arc-bundle.zip
├── main.py              # 平台入口：读需求树 → 生成 DAG → 起内核 → 收集产物
├── verify_node.py       # 验收节点：构建 → 起服 → 跑该节点 spec → 判决
├── octos_stdio.py       # 通过 octos serve --stdio 驱动 Rust 内核
├── arc-policy.toml      # 全部策略旋钮（每个都附动机注释）
├── aria_lint.py         # 从需求文档提取「role + 可访问名」契约
├── template/            # 通用脚手架（规则明确允许）
└── prompts/             # 实现/回归/端口契约提示词
```

zip 里**不含二进制**：评测机运行时按 `main.py` 顶部的 `OCTOS_RELEASE_URL`
现场下载内核，再用 zip 里的 Python 编排器驱动做题。

### 机制清单（按"它解决什么真问题"排）

| 机制 | 解决什么 | 证据 |
| --- | --- | --- |
| **链式 DAG + 修复回边** | 验收失败的具体输出回喂实现节点，而非盲目重写 | 内核 `octos-pipeline` |
| **逐场景隔离 + 种子快照恢复** | 官方 spec 是有状态对，共享启动会互杀 | `08` 运行红线 |
| **ARIA 可访问名契约（D3）** | 需求里反引号名字就是测试定位器，弱模型全丢 | keep 1/32 → 32/32 |
| **aria_lint 契约提取** | 无官方测试时唯一的环内反馈 | bookstack 真捕获 3 处 |
| **多世界工作簿（A20）** | 各族 GIVEN 钉死互斥种子，单一静态种子构造性恒红 | REQ-3 全族解锁，62 → 77 |
| **语法刀** | 修理编辑的不平衡括号让整个脚本死，Playwright 只报远端症状 | `app.js:1242` 缺右括号 = 11 场景全灭 |
| **资产洞探针** | 路由白名单漏一个 .js → 全站 JS 死 → 评分全灭 | github 成品 0/100 根因 |
| **种子金丝雀** | 中段节点把全局 seed() 重写成自身样例 → 毒化 .arc-good | arch-13 6/100 尸检 |
| **停摆刀** | 连续 2 轮场景签名不动 → 节点弃修 | 砍掉"无望节点修复马拉松" |
| **燃料表（双轴）** | 平台计费 ≈ 内核 meter 的 827 倍，$5.5 阈值永不触发 | T1 尸检后重标定 |
| **渐进交付 + 回退链** | 任何时刻被杀都有分，`.arc-good` 保最后过检态 | arch-6 惨案 → arch-7 修复 |
| **自举打包** | 从已验证的高分状态起跑，而不是每次冷启 | 62 分地板多次复现 |

每一条都是**先有尸检、再有刀**——没有一条是"觉得应该有用"加上去的。这是这次
参赛最值得留下的方法论。
