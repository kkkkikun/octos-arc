## 结论

1. **假设①（app 泛化性不足）证伪**：在逐场景注入 REQ-3 Item 世界、REQ-4 公式世界后
   全绿（21/22、16/16）——app 的功能完全跨世界成立。
2. **官方 41 的主体是评分语义，不是应用质量**：
   - 世界失配（不按族重播种）：约 -19 例（REQ-3/4 的文档钉死世界不在 Q3 Sales 里）；
   - 共享会话污染（单 boot 4 workers，无逐测恢复）：再 -40 余例——stateful 链
     （改名/删行/转公开）在并行下互杀，verify_node.py 注释里两次平台 6/100 事故
     记录的正是同一机制。
   - 只有共享 boot 分支能复现 41 的量级（33-35±噪声 vs 41）。
3. **套件已达"文档干净"**：S2 的 103 例中 102 例通过；唯一红 =
   REQ-3-2-1 Sc4，应用在粘贴拒绝时显示 "Please enter a number between 0 and 100"，
   文档在 4 处（L888/L1014/L1286/L1499）钉死 "Please enter a number from 0 to 100"
   ——真实应用缺口，与评分语义无关。
4. 应用侧唯一应改点（文档钉死）：粘贴拒绝文案。次级候选（THEN 细节面）：
   聚合数值、home/editor Last updated 一致性、改名对话框预填——见
   （该文件为运行期临时产物，未留存）（9 条，每条附文档原句）。
5. 平台分若要再抬：逐测试明细（T2 已在台账 #38 申请）到位后，先验证失败是否
   按污染簇分布；共享 boot 语义下任何合规 app 都无法避免 stateful 级联，
   该部分不是 app 的可改进面。

# Github 线：官方前 30 例明细对账（2026-10-02 补）

情报：官方 github 评分前 30 例 = **4 PASS / 26 FAIL**（PASS：1-1-1 Sc3、1-1-2 Sc2、
1-1-2 Sc4、1-1-3 Sc1）。官方套件文件名带描述后缀（`REQ-1-1-1-sign-up.spec.ts` 等），
与两代代理套件都不同——再次证实官方测试从未流出。

## 三类分歧（探针实证）

1. **官方参考种子账号不在文档里**：官方测试用 `org-owner`/`repo-admin`（REQ-2-2-3/
   2-2-4/2-3 共 ≥6 例失败："element(s) not found"）。文档原文只说 "The scenarios
   provide an Owner / a repository Admin"——给角色不给名字。任何只读文档的 app
   都无法种出这些账号 → 结构性不可过。产物实际只种了文档点名的 alice-dev/bob-reviewer。
2. **平台评分态 ≠ 本地模板**：官方 1-1-1 Sc1（nora-demo 注册后可见）、1-1-2 Sc1/Sc3
   （alice-dev "Received: hidden"）在本地产物上全部通过（探针：登录后
   `<span class="nav-username">alice-dev</span>` 直接可见，reload 后仍可见；
   nora-demo 注册→登录→reload 全通）。平台评分时看到的是 hidden menuitem——
   评分态的应用/存储与本地收割的 template 不同（in-run 碎屑或环境差异）。
3. **应用真实缺口（文档钉死）**：`Username already exists` 消息应用其实**有**
   （探针证实），官方 Sc2 失败极可能因其重复用户名是官方种子账号（产物中不存在→
   不判重）。但 **REQ-2-3 的 Manage-access picker 缺少可点击的 'Write' 角色选项**
   （文档钉死 "a combobox 'Role' with clickable role options including 'Write'"）——
   本地两场景 10s 超时，与官方判决收敛（双红，败因不同：官方卡种子名，我们卡 picker）。

## 套件修改（按文档钉死面，本地产物验证通过）

- REQ-1-1-1 Sc2：4 条消息断言改直接文本定位（原 expectVisible 阶梯每探针 ~2.4s，
  4 条纯文本必超 10s 单测时钟——历史遗留超时）。
- REQ-1-1-1 新增 Sc4：重复注册流（L65 钉死 "Username already exists" + 保留尝试值）。
- REQ-1-1-2 Sc2：reload 后用户名直接可见断言（L65 钉死 "the resulting signed-in
  username remains visible after reload"）。
- 本地验证：REQ-1-1 全族 8/8 绿。
- 基线对照：旧套件 × 产物 = **51/100**（REQ-6 全族 1/25——产物是不完整构建，
  T1 github 腿只跑到 21/47 节点）。

## 对 T2 的增量结论

- sheet 的共享 boot 结论得到 github 独立证据支持：官方评分依赖官方参考种子
  （org-owner/repo-admin 一类文档外名字）+ 平台侧状态，两部分都不是 app 可改进面。
- github 产物本身未建完（REQ-6 全族红是真实缺口，但根因是 18h 窗口内 21/47 节点
  没跑完，不是语义问题）——T2 的 github 刀应是「 Completeness」（把剩余节点建完），
  而非 sheet 的「泛化/语义」。

## 标定结果（官方已知 14 例）

| 配置 | 镜像得分 | 与官方判决一致 |
|---|---|---|
| 干净产物 + 官方种子叠加 | 12/14 | 6/14 |
| 碎屑产物（16 垃圾账号）**无**官方种子 | 9/14 | 9/14 |
| 平台官方 | 4/14 | — |

三个机制全部实证：

1. **种子名机制**：无 org-owner 时 2-2-3/2-2-4 翻红（3 例），与官方失败模式一致
   ——官方参考种子账号是文档外知识。
2. **header 用户名机制**：8 个官方 FAIL 全部是断言"登录后用户名立即可见"的用例；
   走菜单路径的官方用例（1-1-2 Sc2）PASS。本地产物的 nav.js 已含修复
   （"stays VISIBLE in the header, not only inside a closed menu"）——
   **平台评的 bank 快照是没有该修复的早期版本**（版本错位，非应用缺陷）。
3. **应用真实缺口**：REQ-2-3 的 Write 角色选项缺失（picker），两配置下皆红，
   与官方判决收敛。

若把 bank 快照换成含 nav-username 修复的版本（或 app 侧同时满足两种读法），
镜像预测官方 8 例翻绿 → github 前段合规度 ≈ 12/14（86%），与 sheet 的 102/103
同级别。**T2 最大的两根杠杆：完备性（github 21/47）与 bank 快照版本管理。**

## Agent 改进建议（证据驱动，按预期分差排序）

1. **完备性优先于深度**（github：21/47 节点 = REQ-4 后半+REQ-5/6 大面积空白）。
   18h 窗口内 breadth-first：每节点先"最小过检"再加深；per-node 时间帽下移；
   未触达节点的最小实现优先于已过节点的修复马拉松。
2. **bank 快照版本管理**：平台评 `.arc-good`（T1 github 停在中途状态，缺
   nav-username 修复）；运行末尾必须强制一次最终 bank + final check_all 后
   重新 bank，绝不让中途旧版代表最终能力。
3. **字面量纪律**：文档带引号字符串 = 硬契约（from 0 to 100 vs between 0 and 100
   教训）。提示词刀：每节点注入「字面量清单」；aria_lint 扩展到消息字面量逐字比对。
4. **双保险交互**：文档绑定的路径全实现（公式栏清格、菜单项），文档未绑定的
   常见路径顺手实现（Delete 键）——单一实现对冲多种读法。
5. **可见状态默认全开**：header 用户名 + 菜单路径同时满足（nav.js 修法即范例），
   消除"立即可见 vs 点开才见"的第三读法敞口。
6. **自建世界探针进在跑循环**：每族验收加一个"外来世界"探针（sheet=空白簿/
   导入簿已建；github=注册全新账号跑全流），泛化缺陷在 run 内暴露而非平台暴露。
7. **共享会话韧性**：官方评分疑似共享 boot（sheet 模拟 33-35≈41）。app 侧降低
   状态耦合（无全局单例残影）；harness 侧最终 bank 前跑一次共享会话自检。
8. **文档外种子零假设**：app 对「任意名字的种子账号/组织存在」保持兼容
   （注册+角色系统天然支持）；同时向平台申诉索取 evaluation seed 说明。
