## 一、初赛规则

### 1. 初赛时间
- **时间范围**：9.24 (0:00) ~ 9.30 (23:59)
- 到期关闭提交入口，正在运行的任务将继续运行直至完成或超出时间上限（见后文）。

### 2. 初赛任务
初赛共设置两个任务。为提高参赛队伍的完赛率，比赛期间将提供：
- 两个任务的需求文档；
- 本地模拟竞赛环境（竞赛平台的 Runner 镜像及核心运行流程说明）。

> **说明**：正式测试用例及单条测试用例的通过信息不对外开放。选手可在评测平台查看某次正式运行的总体测试通过率（两个任务综合计算通过率、开销以及最终得分）。

### 3. 本地练习
比赛期间，赛事方将以队伍为单位，每队 $100\yen \times 5$ 次发放练习券（和之前一样以 `api_key` 的形式，检测到额度低自动补充额度）。

赛事方将开放本地模拟竞赛环境，选手可以在本地复现以下核心流程：
1. 运行智能体；
2. 部署智能体生成的目标应用；
3. 对目标应用执行模拟评测。

本地环境用于验证智能体的运行契约、应用部署方式及基本功能，不包含正式比赛的隐藏测试用例。本地调试结果不等同于正式评测成绩。

本地环境的安装、使用方法，以及平台内部“运行智能体——部署应用——执行 Playwright 评测”的完整流程，请参阅本地模拟竞赛环境：  
[https://github.com/code-philia/hackathon-local-simulation.git](https://github.com/code-philia/hackathon-local-simulation.git)

### 4. 正式提交与评测
初赛提交评分使用独立的 key 来保证消耗计算的准确性，具体规则如下：
- 每支队伍仅可通过队长账号发起正式提交；
- 每支队伍发放 $500\yen$ 比赛券，不限提交次数，用完为止；
- 正式评测使用平台内置的模型 API Key，选手无需上传自己的 API Key；
- 平台将记录每次正式评测产生的模型用量与费用，计算得分后上榜；
- 每次正式提交均会同时运行两个任务。两个任务全部运行结束后，系统生成该次提交的最终成绩；
- 同一队伍不能同时运行两次正式评测。只有当前提交的两个任务全部结束后，队长才可以发起下一次提交；
- **初赛最终成绩采用“历史最高分”原则**：系统从该队伍所有有效正式提交中，保留成绩最好的一次用于最终排名；
- 此外，选手使用个人 API Key 上传平台（练习提交）的次数不受限制，但会占用该队伍评测的资源（有任务运行中不能提交评测），且使用个人 API Key 进行的提交取得的分数不计入最终得分；
- 以上关于“练习券”、“比赛券”的额度设置均为暂定标准（保底），将根据实际使用情况酌情增加。

## 二、计分与排名规则

### 1. 单次提交得分
一次正式提交包含两个任务。排行榜分别展示两个任务各自的测试通过率和开销；排名依据两个任务汇总后的指标计算。

#### 参数定义
- $p$：本次提交两个任务合计通过数除以合计测试数得到的总测试通过率百分数，取值范围为 $0 \sim 100$；
- $b$：本次提交两个任务的总开销（金额 $\yen$），即两个任务开销之和；
- $b_{0}$：每 $1$ 个百分点测试通过率对应的预计开销。如果最终通过率为 $p$，预计合理总开销为 $b_{0}p$；
- $\alpha$：奖励指数。当实际开销低于或等于预计合理总开销时使用该参数；
- $\beta$：惩罚指数。当实际开销高于预计合理总开销时使用该参数。

基于内部测试与研习营数据对测试通过率和开销关系的分析，本次比赛固定使用以下参数：
$$b_{0} = 1.2, \quad \alpha = 0.1, \quad \beta = 0.2$$

#### 得分公式
提交得分 $S(p, b)$ 按以下公式计算：

$$
S(p, b) = \begin{cases}
0, & p = 0 \\
p \cdot \left(\dfrac{b_{0}p}{b}\right)^\alpha, & 0 < p, \; b \le b_{0}p \\
p \cdot \left(\dfrac{b_{0}p}{b}\right)^\beta, & 0 < p, \; b > b_{0}p
\end{cases}
$$

其中，$b_{0}p$ 表示当前测试通过率对应的预计合理总开销：
- 当 $b = b_{0}p$ 时，实际开销与预计合理开销相同，得分等于 $p$；
- 当 $b < b_{0}p$ 时，实际开销低于预计合理开销，使用奖励指数 $\alpha$，得分高于 $p$；
- 当 $b > b_{0}p$ 时，实际开销高于预计合理开销，使用惩罚指数 $\beta$，得分低于 $p$。

### 2. 排名规则
取消低级、高级档，统一按照以下顺序排序：
1. 单次提交得分 $S(p, b)$ 越高越靠前；
2. 若得分相同（由于涉及开销，一般不会出现），比较两个任务的综合测试通过率 $p$，越高排名越靠前；
3. 若得分、综合测试通过率相同，则比较两个任务的总开销 $b$，越低排名越靠前；
4. 若得分、通过率、总开销均相同，则比较提交时间，提交时间越早越靠前。

> **晋级说明**：榜单排名前 20 的队伍将晋级决赛。

## 三、参赛规范与常见问题

### 1. 单个任务允许的最长运行时间是多少？
单个任务的最长运行时间为 48 小时。达到时间上限后，平台将终止运行，以避免模型 Token 无限制消耗。

### 2. 是否允许使用预置脚手架或公共组件库？
允许使用不针对具体比赛任务的通用应用脚手架和公共组件库。例如，下载包中的 `template/` 可以包含目标技术栈的通用初始化框架。  
**不允许**在脚手架、组件库或其他预置文件中包含针对当前任务预先实现的页面、业务逻辑或功能组件。赛事方将对硬编码、预制任务答案等行为进行自动或人工审核。

### 3. 智能体可以不请求大模型吗？
**不允许**。赛事方认为一个不调用大模型（或调用极少次）的“智能体”，本质上是一段固定的程序，无法在两个甚至更多任务上泛化（不得预先写入、复制或直接释放针对具体比赛任务实现的代码，也不得通过其他方式绕过智能体实际完成任务的过程）。赛事方将对“复制预制任务代码”等行为进行审核。

### 4. 参考图在比赛中起什么作用？不读取参考图能否通过全部测试？
参考图用于帮助选手快速理解页面结构、布局和视觉关系。正式测试中的元素定位和交互要求，以需求文档中的描述及场景为准。  
需求文档和场景中未明确要求的内容不会作为功能测试目标。选手使用参考图时，应自行识别并排除图片中的广告、浏览器界面、无关数据等噪声。

### 5. 是否可以下载运行产物和日志？
选手可以下载智能体生成的目标应用。  
平台向选手开放的日志仅包含智能体执行相关内容，不包含正式测试用例的具体执行过程、断言信息或其他可能泄露隐藏测试的内容。

### 6. 运行环境是否允许访问外网？
平台仅放行比赛所必需的网络访问，例如：
- 安装依赖或工具链所需的软件源，如 `npm`、`pip`、`Cargo` 等；
- 调用赛事指定的官方 Meter 或模型服务。

除赛事明确允许的目标外，其他外网访问将受到限制。赛事方将对绕过网络限制、访问未经授权的外部服务等行为进行审核。

### 7. 测试用例的合理性如何保证？
请参考下发竞赛环境中附带的 `public-exercise/arc-bench-lite` 相应需求和测试，了解比赛中测试用例和需求描述之间的对齐关系。

### 8. 如何处理作弊行为或规则边缘情况？
赛事方将结合自动化 Agent 审核与人工审核判断违规行为，包括但不限于：
- 预制或硬编码任务答案；
- 泄露、推测或绕过隐藏测试；
- 绕过平台网络、资源或评测限制。

规则难以覆盖所有边缘情况。如果选手对某项实现方式是否合规存在疑问，请在采用前联系赛事工作人员确认。
